# 企画相談と要件定義（Pick Your Agent Project）

> [!NOTE]
> **HITMAN 使用証跡**: 企画書の提出用コードブロックは `scripts/brief_check.py` が出力する（1行目に `[skill:pick-your-agent-project@v1]` が自動で入る）。手で書いたり書き換えたりしないこと。

このスキルのゴールは、**受講生が作りたいものをそのまま**、研修で実装・検証できる形の要件定義書に落とし込むことです。
あなた（Antigravity）が相談相手です。HITMAN はこの企画書を検査し、その内容に合わせて T-3 以降の手順を作ります。**企画書に書いたものが作られ、書いていないものは作られません。**

## やってはいけないこと

- **受講生の企画を、よくある別のもの（チャットBot、WBS管理、ログ解析など）に置き換えない。** 「カレンダーアプリ」と言われたら、カレンダーとして使える画面を持つアプリとして設計する。
- **例やテンプレートを、そのまま企画として出さない。** 例は受講生が迷ったときの発想の手がかりにだけ使う。
- **受講生の合意なしに企画書を書き上げない。** 機能・画面・今回作らないものは、必ず受講生に確認してから決める。
- **API キーを聞かない・書かない。** キーの設定は T-3 で `ipp-secure-credentials` スキルを使って受講生がエディタで行う。

## 進め方（対話。1回の発言で質問は1〜2個まで）

### 1. 作りたいものを聞く
「どんな場面で、だれが、何に困っているか」「今はどうしているか」を聞きます。アイデアがない人には、普段の業務や生活の困りごとを1つ聞き、それに合わせた案を2〜3個出します。

どうしても決まらない場合は、「HITMAN の画面でコースB（HITMANクローン構築）を選ぶと、お手本どおりに進められます」と案内してよい（受講生が選んだときだけ）。

### 2. 機能を広げる
受講生の言葉から機能の候補を挙げ、「こういうこともできると便利ですか？」と提案して**機能を拡充**します。観点：

| 観点 | 問いかけの例 |
|---|---|
| 画面 | どんな画面で使いたいですか？（カレンダー、一覧表、グラフ、入力フォーム、チャット…） |
| AI の役割 | AI（Gemini）に任せたいことは？（要約、分類、提案、文章作成、画像の読み取り、質問への回答…） |
| ツール | AI が実際に行う処理は？（データの登録・検索・集計・計算、ファイルの読み取り…） |
| データ | 何を記録・保存しますか？ 再起動しても残す必要がありますか？ |
| 記憶 | 利用者の好みや前回の内容を覚えておくと便利ですか？（`memory-bank-setup`） |
| 資料検索 | 回答の根拠にしたい資料はありますか？（`rag-engine-setup`） |

### 3. 研修で作れる範囲に絞る（正直に伝える）
次の条件に合わない機能は、受講生に理由を説明し、**代わりの形を提案**するか『今回は作らないもの』に入れます。黙って落としたり、別の機能にすり替えたりしないこと。

- 作れるもの: Python（FastAPI）＋ HTML/CSS/JavaScript の Web アプリ。**画面のボタン・入力フォーム・カレンダー・グラフは自作の HTML で作れる。** AI 部分は Google ADK のエージェント（Gemini）＋自作の関数ツール。
- AI チャットの中に出す A2UI カードは表示専用（ボタンは動かない）。操作が必要なものは、アプリの画面側（HTML）に作る。
- データ保存: 研修ではメモリ・ローカルファイル（JSON / SQLite）が基本。Cloud Run では再起動で消える。消えては困る場合は Firestore 等を使う（難易度が上がることを伝える）。
- ログイン・権限管理・複数人での共有・メール送信・外部サービス連携（社内システム、SNS など）は研修時間では難しい。必要なら『今回は作らないもの』へ。
- 機能は **研修時間で作れる数（目安 3〜6 個、最大 12 個）** に絞る。

### 4. 企画書を書く → 受講生に確認する
下の書式で `ipp-agent-workspace/project_brief.md` を作り、内容を受講生に見せて「この内容で進めてよいですか？」と確認します。修正の要望があれば直して、再度確認します。

### 5. 書式を検査して、HITMAN 提出用ログを出す
受講生が合意したら、ワークスペースのルートで実行します：

```bash
python .agents/skills/pick-your-agent-project/scripts/brief_check.py ipp-agent-workspace/project_brief.md
```

- `BRIEF_CHECK: FAIL` の場合は、表示された点を受講生と相談して直し、再実行します。
- PASS したら、スクリプトが出力したコードブロックを **一字一句変えずに** 回答の最後に出力し、受講生へ「上のコードブロックをコピーして HITMAN のチャット欄に貼り付けてください」と案内します。

## 企画書の書式（見出しと項目名は変えないこと）

```markdown
# <表示名>: Project Brief

## 1. 基本情報
- エージェント名: <英小文字スネークケース 例: calendar_journal_agent>
- 表示名: <画面に出す名前>
- 利用者: <だれが使うか>
- 解決する課題: <どんな困りごとを解決するか>

## 2. 機能一覧
- F1: <機能> ／ 受け入れ条件: <どうなれば完成か（画面で何ができる・何が表示される）>
- F2: <機能> ／ 受け入れ条件: <どうなれば完成か>

## 3. 画面
- S1: <画面名> ／ 要素: <入力欄・ボタン・一覧・カレンダー・グラフ・AIチャット欄 等> ／ 使う機能: F1, F2

## 4. 関数ツール
- <関数名>(<引数>: <型>, ...) -> <返り値> ／ 役割: <何をするか> ／ 使う機能: F1

## 5. データと保存先
- <データ> ／ 保存先: <メモリ / ローカルファイル / Firestore 等>

## 6. 認証情報
- GEMINI_API_KEY: ローカルは .env から読み込む。本番（Cloud Run）は Secret Manager から渡す。キーの値はどこにも書かない。

## 7. 今回は作らないもの
- <研修時間内では作らない機能（なければ『なし』）>

## 8. 動作確認
- Q1: <エージェント（AI）への質問1。ツールが呼ばれる内容にする>
- Q2: <内容がはっきり異なる質問2>
```

書式のルール（`brief_check.py` が検査します）：
- すべての機能（F1, F2 …）に受け入れ条件を書き、どこかの画面またはツールの『使う機能』に入れる。
- 関数ツールは、引数に応じて実際に処理するもの（固定値を返すだけのダミーは T-3 で不合格になる）。
- Q1・Q2 は T-3 のスモークテストでそのまま使われる。ツールが呼ばれ、内容がはっきり異なる質問にする。ダブルクォート（"）は使わない。
