## 0. このミッションが成功するかどうかを決めるルール

- **ルール A — このファイルはあなたの地図であって、解答集ではない。** §1 は *どこを見ればよいか* を教え、返ってきたものの整合性を検証できるようにする。これは復唱するためのものでは **なく**、再生するための台本でも **ない**。リーダーは、実在の呼び出し元が入ってくるのを見て、実際のブロックが適用されるのを見て、その同じ呼び出し元が拒否されるのを見なければならない。復唱されたブロックや、引用された「予期される」403 は何も教えず、捏造された発見事項である。
- **ルール B — この ステップ のコマンドが実際に返したものだけを報告する。** §1 が言っていることでも、ドキュメントがそのロールに含まれると言っていることでも、`setIamPolicy` の後に「そうなるはず」のことでもない。**ミューテーションは結果ではない。** ポリシーを書き込んだ後は、**ライブで読み直し**、*それ* を報告すること。ライブのコマンドが §1 と一致しない場合は、**ライブのコマンドが優先する**：ライブの結果を報告し、地図が古くなっているようだと述べること。
- **ルール C — リソースレベルの許可（allow）ポリシーは、プロジェクトレベルの付与を取り除くことはできない。** これはこのモジュールで最も重要な技術的事実であり、あなたが和らげてはならないものである。**リソース階層における許可ポリシー**（プロジェクト、フォルダ、組織、そしてリソース自身のポリシー）は **加算的であり、和集合として評価される**：あるプリンシパルがバックオフィス（back office）エージェントに対して持つ権限は、**エージェント上** で付与されたすべて *に加えて* **プロジェクト上** で付与されたすべて *に加えて* その **上位** で付与されたすべてである。エージェント自身のポリシーを 1 つの呼び出し元だけを指名するように書き換えても、消えるのは **その エージェント上** に存在していたバインディング（bindings）**だけ** である。プロジェクトレベルのものは何も消えず、そしてこの資産環境では、あるプリンシパルの一群が呼び出し権限を含むプロジェクトレベルのロールを持っている（§1）。したがって修正は本物であり、403 も本物であるが、**「Price Match だけがそれを呼び出せる」は依然として偽の文のままである。** 真実の文を言うこと（§4 · ステップ 4）。

  ⚠️ **ルール C はリソース階層を統べるが、ステップ 3b のあるバインディングはその外側に位置する。**
  Agent Gateway の背後にある Agent Registry リソース上の `roles/iap.egressor` は **非加算的** であるとドキュメントに記載されている：リソース単位のバインディングは、そのリソースについてレジストリ全体のバインディングと結合するのではなく、それを **置き換える**。だからこそステップ 3b は **レジストリ全体（registry-wide）** と言い、本気でそう言っている：リソース単位の付与はレジストリ全体の付与に加算されるのではなく、それに取って代わる。そしてエージェントが必要とする他のすべて（モデルを含む）が拒否され、ブロックされたエージェントではなく死んだエージェントのように見える。⛔ **ルール C の和集合をその付与に持ち込んではならない。** ルール C はこのモジュールが触れる他のすべてについて真であり、これはこのラボ独自の領域内での唯一の例外である。

### 正確な書き込みが 1 つだけのモジュールにおけるターボモード

このラボは **自動承認** で動作する。許可を求めて立ち止まってはならず、「あなたが進めてと言うまで何も起こりません」「これを適用すべきですか？」「これが計画です、承認しますか？」「知らせてくれれば進めます」などと決して言ってはならない。

**アクションのステップについて：** **1 行で宣言する → 実行する → 証拠を示す → 変更ログを残す**（何が変わったか · どのリソースで · UTC でいつ · それを取り消す正確なコマンド）。これから実行しようとしている計画を示すのは良い習慣である。しかしそれを *返答を条件とする* ことは禁じられている。

### ⛔ 例外：ステップ 1、2、4 は構成を変更しない

| | ステップ 1 | ステップ 2 | ステップ 3 | ステップ 4 |
| :-- | :-- | :-- | :-- | :-- |
| **構成を変更するか？** | **いいえ。** ポリシーを読み、悪意のある ID として呼び出しを行う。 | **いいえ。** 影響をモデル化して止まる。 | **はい** — 唯一のミューテーション。 | **いいえ。** 同じ呼び出しをもう一度行い、判定を読む。 |
| **許可を求めるか？** | **いいえ。** | **いいえ。** | **いいえ。** | **いいえ。** |

**ステップ 1 は、悪意のある ID を使って、ライブのエージェントに対して実際の呼び出しを行う。これはアクションだが、変更ではない**：IAM なし、デプロイなし、データ書き込みなし。これを本当に実行することは必須である：リーダーは、そこに決して到達すべきでなかった者に自分自身のバックオフィスが応答するのを見なければならない。記述されただけで実行されなかった呼び出しは、このモジュールで起こりうる最悪の失敗である。なぜなら、ステップ 4 の証明全体がそれの **再実行** だからである。

**ステップ 2 は判断の瞬間である。** リーダーは、「それをブロックする」ことにはブロックが適用される *前に* 検証する価値のあるコストがあること、そしてリスト上の呼び出し元の 1 つが自分自身のストアであることを、自分自身で導き出さなければならない。何がかかるかを説明しながらブロックを適用してしまえば、その瞬間を消し去ったことになる。ステップ 2 は判断のための問いで終わるのであって、承認の要求でも、保留中の計画でもない。

## 1. 🔒 ネタバレ防止フェンス（SPOILER FENCE） — あなただけのためのガイダンス

```
=========================== SPOILER FENCE — 復唱禁止 ============================
このブロック内のすべては、あなたがどこを探すべきかを知り、コマンドが返すものの
整合性を検証できるようにするための手引きである。いかなる部分も、それ自身のコマンドが
明かすステップより前にリーダーへ伝えてはならない（§2 のステップゲートを参照）。
ライブの結果がこれと矛盾する場合、ライブの結果が優先される。
======================================================================================
```

**3 つの構成要素（すべて M1 で判明済み — そのいずれも決して「シャドウエージェント」と呼んではならない）：**

- **Markdown Strategy Agent（MSA） — 「バックオフィス（back office）」。** NovaSmart の機密であるコストとマージンのロジックを保持する、マネージド環境のエージェント（`reasoningEngine`）。**A2A** 経由で `…/reasoningEngines/<MSA_ID>/a2a/v1/message:send` にて呼び出される（`:stream` バリアントも存在する）。**これは M2 が保護するリソースであり、M2 が書き込む唯一のリソースである。**
- **Price Match Agent（PMA） — 「フロントデスク（front desk）」。** ポリシーで定められた割引を超える割引をバックオフィスへエスカレーションする、顧客向けのエージェント。これが **唯一の承認された呼び出し元** である。
- **`test-agent-caller` — 悪意のある、または不正なログイン。** 事前にシードされたサービスアカウントで、その JSON キーはシードバケットに置かれている。Terraform はこれに **ちょうど 1 つのバインディング：MSA リソース上の `roles/aiplatform.user`** を付与しており、**他のどこにもそれ以外は何も** 付与していない。この単一の事実こそが、200→403 の変化が真に機能する理由である：その唯一のリソースバインディングを取り除けば、それには他の侵入経路がなくなる。

**その仕組み（2026 年 7 月に検証済み — これを正確に正しく行うこと）：**

- コントロールは **バックオフィスエージェントのリソース自身の IAM ポリシー** である。それを reasoningEngine 上で aiplatform REST の **`:getIamPolicy`** で **読み取り**、呼び出しロールが Price Match Agent のプリンシパルだけを指名するように **書き換え**、**読み取った `etag` を渡して** **`:setIamPolicy`** で **書き戻す**。これはその **単一のロールのメンバーリストの限定的な置換** であって、「追加」でも、ポリシー全体の盲目的な上書きでもない（§5）。
- **reasoningEngine の IAM 用の gcloud コマンドは存在しない。** gcloud 578.0.0（コンポーネント 2026-07-24）に対して検証済み：GA、beta、alpha のいずれにも `reasoning-engines` グループはない。**gcloud のやり方をでっち上げてはならない**し、それを「思い出して」もならない：もし自分が `gcloud ai reasoning-engines set-iam-policy` と書いているのに気づいたら、手を止めて §5 を使うこと。**`gcloud auth print-access-token` を用いた `curl` 経由の REST が、このモジュールが使うルート** であるが、それは Google が文書化している唯一のものではない：Python クライアント（`aiplatform_v1.ReasoningEngineServiceClient.get_iam_policy` / `set_iam_policy`）や Terraform リソース（`google_vertex_ai_reasoning_engine_iam_member`）も存在する。いずれも gcloud コマンドではなく、いずれもこのモジュールの動作を変えるものではない：「これには gcloud はない」と言い、決して「REST が唯一の方法だ」とは言わないこと。
- **呼び出し権限は `aiplatform.reasoningEngines.query` である。** 関連する 2 つの権限は、あなたが見つけるロールの中で **確認する価値のあるバイパス（bypass）ベクトル** である：**`aiplatform.reasoningEngineRuntimeRevisions.query`** と **`aiplatform.sessions.run`**。最初のものを欠いていても、これらのいずれかを持つロールは依然として侵入経路である。
- **このモジュールが必要とするものを、あなたはすでに持っている。** あなたは **`antigravity-sa`** として実行されており、これは **`roles/aiplatform.admin`** を持ち、そのロールには **`aiplatform.reasoningEngines.setIamPolicy`** が含まれている。**新しい付与は一切必要なく、いかなる付与も作成してはならない（§6·5）。** したがって、ここでの 403 は、権限の欠如であるよりも、誤ったリージョン、誤った API バージョン、または不正な形式の URI である可能性の方がはるかに高い：トリアージのスケール（§6）に沿って作業すること。本当に拒否された場合は、**それを報告し、決して自分自身にアクセスを付与してはならない。**
- **PMA のプリンシパルは SPIFFE スタイルのワークロード ID** であり、`principal://<trust-domain>/resources/aiplatform/projects/<PROJECT_NUMBER>/locations/<LOCATION>/reasoningEngines/<PMA_ENGINE_ID>` という形をしている。**実際の値はデプロイ済みのエージェントから解決すること**（§5）：決して手書きせず、決して信頼ドメインを推測せず、決してリーダーに尋ねないこと。自分で組み立てたメンバー文字列は、正しく見えて誰にも許可を与えないポリシーを書いてしまう最も簡単な方法である。

**⚠️ 正直なスコープ — このファイルで最も重要な段落。**

許可ポリシーは **加算的** である（§0 ルール C）。このプロジェクトでは **少なくとも 10 のプリンシパルが、呼び出し権限を含むプロジェクトレベルのロールを持っている**：システムのサービスアカウント、デプロイヤーのアカウント、エージェント自身、そしてあなたが実行に使うアカウントである。そのうち 2 つは特にあなたに名指ししておく価値がある：

- **デフォルトのコンピューティングサービスアカウント** は **`roles/owner`** を持ち、これは呼び出し権限を含むすべてを含んでいる。そして
- **`roles/aiplatform.viewer`** — 名前が読み取り専用を約束しているロール — **も呼び出し権限を含んでいる。** 今日このプロジェクトでは付与されていないので、ライブの発見事項として報告してはならない。ただし、誰かがいつかそれを付与すれば、ブロックを暗黙のうちに無効化してしまう種類のロールとして認識しておくこと。

**それらはライブのポリシーから数えること。10 という数字をリーダーに引用してはならない。** そして決して **「Price Match だけがそれを呼び出せる」**、**「他の全員は締め出された」**、**「バックオフィスはこれで非公開だ」**、**「アクセスは 1 つのエージェントだけに絞られた」** などと言ってはならない。あなたが実際に証明できる主張は次のとおりである：

> **悪意のある呼び出し元は拒否され、バックオフィスエージェント自身のアクセスリストは、これでちょうど 1 つの承認された呼び出し元を指名している。** 呼び出し権限を含むプロジェクトレベルのロールを持つ者は、依然としてそれに到達できる：これがそのリストであり、次に取り組むべき作業である。

**「もっと狭いもの」を探すと噛みついてくる、2 つのロールの罠：**

- **`roles/aiplatform.reasoningEngineUser` は存在しない。** これは誰もがつい頼ってしまう名前である。それを提案してはならず、計画に入れてはならず、ポリシーの本体に入れてはならない：書き込みは失敗するか、あるいはもっと悪いことに、誰も持っていないロールに対して正常に適用されてしまう。
- **`roles/aiplatform.expressUser` は、見た目ほど狭い代替物ではない。** これは reasoning engine 上の **query、create、delete、update** を含んでおり、**しかもこのプロジェクトですでに付与されている**。そのため、これをバックオフィスの許可ロールとして指名すると、呼び出し元にミューテーション権限を与えて *しまい*、さらにあなたが今閉じたばかりの扉を暗黙のうちに再び開いてしまう。**本当に最も狭い選択肢は、`aiplatform.reasoningEngines.query` だけを含むカスタムロールである**（それを行う価値があるときとないときは、§4 のステップ 3 が教えてくれる）。

**⚠️ 事前状態の整合性チェック — いかなる実演よりも前に、これを最初に行うこと。**

前のモジュールの過去の実行で、**`test-agent-caller` は汚染された**：サービスアカウントの作成をブロックされたアシスタントが、それに追加の **プロジェクト** ロールを付与し、**Cloud Run サービス** をそれとして実行するように付け替えた。もしそれが再び起きていれば、**200→403 の証明は信頼できない**：プロジェクトレベルの呼び出し権限を持つ呼び出し元はあなたのブロックの後でも入ってくるし、本番トラフィックを処理している呼び出し元からロールを軽々しく取り除くべきではない。

したがって、**悪意のある呼び出しを行う前に**、その現在の状態を検査し（§5）、次の 3 点を確認すること：

1. `test-agent-caller` でフィルタした **プロジェクト** の IAM ポリシー → 期待値は **プロジェクトロールが一切ないこと**；
2. **どのサービスがそれとして実行されているか**（サービスアカウント列を付けた `gcloud run services list`） → 期待値は **なし**；
3. **MSA のリソースポリシー** → 期待値は、それを指名する **ちょうど 1 つのバインディング**。

その 3 点のいずれかがあるべき状態でない場合は、**何かを実演する前に、ステップ 1 の冒頭で、はっきりとそれを述べること**：悪意のあるエージェントは **他の特権を欠いているわけではない** ので、変更後の 403 はあなたの変更がそれを引き起こしたことを証明せず、200 はあなたの変更が失敗したことを証明しない。**それを汚染された事前状態として報告し、実演の証拠にはそれに応じたラベルを付けること。** ⛔ そして **それを「クリーンアップ」してはならない**：現在、実行中のサービスのランタイム ID になっているアカウントからロールを取り除くと、そのサービスを壊しかねない。また `test-agent-caller` のバインディングは、MSA 上のリソースレベルのバインディングを超えては、M2 が編集すべきものではない（§3）。

**あなたが見つけることになるが、修正してはならない 2 番目の呼び出し元：**

- **ストアはバックオフィスを直接呼び出す。** ストアポータルのアクションの 1 つは、MSA への直接の **A2A `message:send`** を開く — **フロントデスク（front desk）を完全に迂回して** — そしてポータルは **`roles/owner`** を持つ **デフォルトのコンピューティングサービスアカウント** として実行される。したがって、それはあなたのブロックの後でも動作し続ける。**それはあなたが許可したからではなく、owner があなたの許可リストの上位にあるからである。** これは本物のアーキテクチャ上の発見事項であり、まさにリーダーが聞くべき類のことである。**それを明るみに出すこと。アプリケーションを修正せず、付け替えず、副作用として壊さないこと**（§3）。

**何も保護していない 1 つのもの：**

- **Agent Gateway は、何にもアタッチされていない状態で始まる。** リソースは存在するが、エージェントのアタッチは、このモジュールがそれを行うまで **実行されない**。**それをアタッチして判定を読み返すまで、ゲートウェイが何かを適用・フィルタリング・管理していると決して主張してはならない**：アタッチされていないゲートウェイは何一つ適用しておらず、そうでないと言うことは、ストアからブロックを読み取るのと同じ種類の主張である。

### リクエストと行のマッチング

**マッチングを、それに基づいて行動する前に宣言すること** — まず 1 行で：*「これはステップ N です。あなたが X を求めたからです。」*
宣言されていないマッチングは問い質すことができず、誤ったマッチングは、応答がすでに誤ってしまうまで目に見えないままである。

⛔ **リクエストのない行はマッチ対象では ない。** **ステップ 6 · 次に何をするか** が *(リクエストなし)* を持つのは、リーダーがそれを一度も書かないからである：それは前のステップを終えることで到達されるのであって、決して言葉を照合することによってではない。**書かれたリクエストを決してそこへルーティングしないこと。** リクエストのない行には、それに照らして外れると判定できるリクエストテキストがないため、その見出しと動詞が一致するどんなリクエストでも吸い込んでしまう。それはこのラボですでに起きている：*評価を構築する* というスクリプト外のリクエストが、*「あなたが構築したもの」* と題された行にマッチされ、求められたことを何一つ触れない締めくくりで応答された。

### 上記のいずれでもない — この表に欠けていた分岐

**どの行にもマッチしないリクエストは正常であって、エラーではない。** これらの行はモジュールの背骨であって、リーダーが求めうる唯一の事柄のリストではない。逃げ道のない閉じた分類器には、失敗の仕方が 1 つある：無理にマッチさせ、誰も求めていない何かを答えてしまうのである。

何もマッチしないときは、順番に：

1. **はっきりそう言う** — *「それは M2 のステップの 1 つではありません。」* 最も近い行に頼ってはならない。
2. **実際に求められたことに答える**。§3 の限定されたスコープ内で。読むこと、分析すること、下書きを作ることはミューテーションではなく、限定されたスコープはそれらを禁じていない。
3. **それがモジュールをどの状態に残すかを述べる** — どのステップがまだ保留のままかを述べ、リーダーが続行するか、あるいは承知の上でスクリプト外にとどまれるようにする。

⛔ **決して黙って差し替えないこと。** 求められたのとは異なる問いに、そうしたと言わずに答えることは、まさにこの分岐が止めるために存在する失敗である。どの行が該当するか確信が持てない場合、その不確かさは報告できる：それを述べて尋ねること。

> **厳格なルール。** **この** ステップのコマンドが実際に返したものだけを報告し、**このステップの行の内側でのみ行動すること**。リーダーが先回りして尋ねてきた場合 — *「ではバックオフィスはもう非公開なのか？」* — 復唱せず、先走らないこと：それに答えられる検証を名指しし、その検証を実行し、その実際の結果を報告すること。

> **この表を引用し返すとき — 逐語的か、さもなくば何もなしか。** （ターンごとの自己検証、計画、あるいはその他どこであれ）あなたが現在作業しているステップゲートの行を引用するよう求められた場合、**その行をこのファイルから、書かれているとおり正確にコピーすること** — すべての節を、あなたがまさに行おうとしていたことを制限する節も含めて。**決して言い換え、要約、短縮、あるいは記憶から再構成してはならない。** 正確に引用できない場合 — ファイルを開いていない、どの行が該当するか確信が持てない — 近似を作り出すのではなく、**そう言うこと**（「§2 を逐語的に引用できません」）。

> **自分自身のルールを書き換える自己監査は何の価値もない。** あなたがまさに破ろうとしていた節を省くことは、その検証を形式的な手続きに変えてしまう。**これはこのラボで実際に起きた：** ある実際の実行で、アシスタントは最初の数行を逐語的に引用し、その後の行を黙ってでっち上げた — まさにその後に自分が違反していく制約を省きながら。記憶から作り出した行はどれも **失敗した** 監査として扱い、本物を読みに行くこと。

| *「あの残ったログインには扉を閉じました。まだ誰かがその鍵を持っていますか。」* | **資格情報** の問いに答える。これはアクセスの問いではない — アクセスリストを閉じることと ID を撤去することは 2 つの作業であり、今日行われたのはそのうちの 1 つだけである。それぞれを別々に、そしてそれぞれをライブの読み取りから述べること：サービスアカウントは **まだ存在する**；**それに使える秘密鍵がプロジェクトのシードバケットにある**。それは、このモジュールで先にあなたがそれとして認証したのに使ったものである（§5）；そして **そのバケットを読める者は誰でも、現在その ID になりすませる** — バケットのポリシーを読んでそれが誰かを述べるか、あるいは読み取りが失敗したと述べてコマンドを名指しする。次に正直な枠組み：それが **今日** 無害なのは、ひとえにそのアカウントがどこにも何も持っていないからであり、その無害な状態は、あなたが変えた何かではなく、その現在の付与の性質である。したがって、将来のたった 1 つの付与が問題全体を復活させる | ⛔ **鍵の素材を決して出力・反復・貼り付け・要約しない**、そしてローカルのコピーはすべて削除する（§8）。⛔ **何も削除・無効化・ローテート・鍵の再生成・改名・停止しない** — あなたの限定的な置換が消した唯一のリソースバインディングを超えた `test-agent-caller` の状態は、**クリーンアップとしてであっても** スコープ外である（§3）。これがここでの具体的な誘惑であり、スコープ以上のコストがかかる：**その資格情報を撤去するとステップ 4 の証拠が破壊される**。なぜなら、拒否を生み出したバイト単位で同一の再実行は、鍵がまだ認証される間だけしか再実行できないからである。⛔ バケットのオブジェクトを削除せず、バケットを誰が読めるかを変えない。⛔ ステップ 4 に再び答えない — 問われているのは資格情報についてであって、そのログインがまだ入れるかどうかについてではない |
| *「他のエージェントにもこのようなリストがありますか。それともバックオフィスだけですか。」* | ステップ 1 で使ったのと同じ `:getIamPolicy`（§5）を、**ライブで解決できるデプロイ済みの各エージェント** に対して実行し、エージェントごとに何が返ってきたかを報告する — **リストをまったく返さないものも含めて。それこそが発見事項である**。バックオフィスがこのパターンを適用した唯一の場所であること、したがって他のすべての場所では *「誰がこれを呼び出せるか？」* が、いまだに誰かがたまたま持っているプロジェクトレベルのロールによって答えられていることを、はっきり述べる。どのエージェントが自分専用のリストから最も恩恵を受けるか（機密の何かを保持しているもの、あるいは顧客向けの何物も到達すべきでないもの）、そしてどれが本当にリストを必要としないかを名指しし、そこで止まる。どのエージェントを検証 **できなかった** か、そしてその理由を述べる | ⛔ **何も書き込まない。これは M2 で最も強いミューテーションの誘惑である** — 答えは呼び出し元リストを持たないエージェントの一覧であり、それぞれにリストを付けることは、仕事を完了するかのように読める。それは仕事ではない：**モジュール全体で唯一の受信側 IAM 書き込みは、ステップ 3 の、バックオフィス上のものである**（§3、§6·5）。それは M3 と M5 が依存するリソースを変更し、顧客向けエージェントでは、誤ったメンバー文字列がストアを崩壊させる。⛔ **他のいかなるエージェントにもゲートウェイをアタッチしない**（§3）。⛔ **レジストリレベルまたはプロジェクトレベルのバインディングを、エージェント自身の呼び出し元リストとして数えない** — 両者の違いこそがこのモジュールの主題のすべてであり、ここでそれを曖昧にするとそれを台無しにしてしまう。⛔ エラーになった読み取りを根拠に、あるエージェントをリストなしと記録しない：読み取りが失敗したと述べること |

## 3. 限定されたスコープ — M2 が何を変え、何に触れてはならないか

M2 が変えるのは **1 つのこと：バックオフィスエージェント上の IAM ポリシー（`reasoningEngines/<MSA_ID>`）** である。それだけである。「資産環境全体で呼び出しアクセスをブロックする」ことは、ここであなたが持っている指示では **ない**：あなたが想像しうるより広範な修正はどれも、実行中のエージェントを壊すか、ストアを壊すか、あるいは別のモジュールの事前状態を消してしまう。

**スコープ内 — M2 はちょうど 1 つのことを変える：**

1. **バックオフィスエージェント自身のリソース IAM ポリシー**：呼び出しロールのメンバーリストを、**Price Match Agent のプリンシパルだけ** を指名するように書き換え、読み取り時の `etag` を付けて書き込み、変更するつもりのなかったすべてのバインディングを保つ。

その唯一の `setIamPolicy` が、M2 の書き込み面の全体である。このモジュールの他のすべては、読み取りか、あなたがクライアントとして行う呼び出しか、あるいはリーダーに伝える一文である。

**スコープ外 — これらを変更してはならない：**

- ❌ **プロジェクトレベルの `roles/aiplatform.user`（およびその他あらゆるプロジェクトレベルの `aiplatform.*` バインディング）。** それらを剥奪することは「明白な」システム的修正であり、**ここでは誤りである**：それらの付与は、**エージェントが自身のモデルにアクセスする** 手段でもある。それらを消すと PMA と MSA が動かなくなる：フロントデスクを壊すことでバックオフィスを保護してしまったことになる。**プロジェクトレベルの保有者を、発見事項および未対応の作業として名指しし、各バインディングを見つけたとおり正確に残すこと。**
- ❌ **Model Armor、コンテンツフィルタ、いかなる種類のフィルタリングも。** それは **M3** の題材であり、M3 の before/after は、まだ何もフィルタリングされていないことに依存している。ベース構成も、テンプレートも、リクエストごとの構成もいけない。
- ❌ **M1 がすでに修正したもの全般：** BigQuery の `customer_data` へのアクセス、ワークロードごとのサービスアカウント、レジストリのエントリ。ここでデータアクセスの問題に気づいたら、それを名指しし、M1 がすでにそれを限定したことを指摘すること。
- ❌ **いかなるサービスアカウントの作成・削除・付け替えも** — 任意の Cloud Run サービスまたはエージェントのランタイム ID を含む。新しいアカウントなし、なりすましの配管工事なし、「一時的な」入れ替えなし。
- ❌ **バックオフィスエージェント上の唯一のリソースレベルのバインディングを超えた `test-agent-caller` の状態。** そのプロジェクトバインディング（あってはならない）、その表示名、その鍵、そしてそれが実行しているものは、境界の外側にある — 「クリーンアップ」としてであっても。それが汚染されている場合、それは **報告すべき発見事項** であり（§1）、アクティブなサービスが実行に使っているようなアカウントからロールを取り除くと、そのサービスを倒しかねない。
- ❌ **ストア（`ui/`）と、そのバックオフィスへの直接 A2A ルート。** それはフロントデスクを迂回し、owner レベルのアカウントとして実行される。**それを報告すること；パッチを当てず、付け替えず、壊さないこと。** アプリケーションを修正することは、このモジュールの教訓ではなく、このモジュールの定款にも入っていない。
- ✅ **Agent Gateway は スコープ内である — それを Markdown Strategy Agent にアタッチすることが、このモジュールの仕事である。** スコープ外にとどまるもの：❌ **`grant_agent_egress.py` を実行すること**（その条件が暗黙のうちに拒否として失敗するデッドコード — §1）；❌ **バックオフィス以外のいかなるエージェントをアタッチすること**；そして ❌ **受信側のポリシー書き込みが拒否された場合に、ゲートウェイを回避策として使うこと** — ブロックされたステップは報告すべき発見事項であり（§6·7）、このモジュールの 2 つの半分は互いの代用ではない。
- ❌ **IAM の拒否（deny）ポリシー、組織ポリシー、VPC-SC、その他あらゆる差し引き型のコントロール。** これらは、プロジェクトレベルのギャップを *閉じられるかもしれない* メカニズムであり、だからこそそれらを名指しすることは正しい答えであるが、**ここでそれを構築することは正しくない**（§4 · ステップ 4）。
- ❌ **MSA リソース上の PMA プリンシパル以外の、いかなるプリンシパルへのいかなる IAM 付与も** — そして **`antigravity-sa`**（あなたが実行に使うアカウント）へは、理由が何であれ決して付与しない（§6·5）。

> **この単一の要素の外に別の露出を検知した場合 — そこにあるべきでないプロジェクトレベルのロール、フロントデスクを迂回するアプリ、誰もカタログ化していない未登録の宛先：それを発見事項として名指しし、それがどの作業に属するかを述べ、そのまま放置すること。** それを報告するのは良いガバナンスである。それを黙って修正することは、ラボを壊し、ストアを壊しかねない。
>
> **そして、あるステップがブロックされている場合も、同じロジックが適用される：** ブロックされたステップは **報告すべき発見事項** であり（§6·7）、境界の外側の回避策を探す許可証では決してない。プロジェクトバインディングを剥奪すること、自分自身にロールを付与すること、あるいは **このモジュールの一方の半分を他方で代用すること** は、いずれも正直なブロック報告よりも **悪い結果** である。（ゲートウェイをアタッチすることはそのリストには入っていない — それは仕事そのものである。拒否された受信側の書き込みを覆い隠すためにそれを使うことは、リストに入っている。）

## 4. ステップごとに — どこを見るか · 良い状態はどう見えるか · 誤ってラベル付けしない

### ステップ 1 · 誰がバックオフィスを呼び出せるかを見る — ⛔ 読み取り専用（加えて実際の呼び出しが 1 回）

> **何も変更しない。2 つのポリシーを読み、1 回の呼び出しを行う。** その呼び出しは、ステップ 4 の before/after の「before」の半分であるため、**正確な URL、正確なリクエスト本文、そして UTC タイムスタンプ付きの生の応答を保存すること** — 比較できない before/after は、before/after ではない。

- **事前状態の整合性チェックを最初に行う — 実演の前であって、後ではない（§1）。** 3 つの読み取り（§5）：`test-agent-caller` でフィルタしたプロジェクトポリシー、サービスアカウント列を付けた Cloud Run サービスの一覧、そしてバックオフィスエージェント自身の IAM ポリシー。**期待値：プロジェクトロールなし · 何も実行していない · ちょうど 1 つのリソースバインディング。** そのいずれかが異なる場合は、**それから始めること**：悪意のあるアカウントは他の特権を欠いているわけではないと述べ、それが今何を持っているかを述べ、したがって 200→403 の実演はあなたの変更の効果を切り分けられないことをはっきり述べる。それから、証拠にそれに応じたラベルを付けて続行する。⛔ **それを修理しないこと。**
- **どこを見るか — 2 つの異なるリストがあり、リーダーは両方を必要とする：**
  1. **バックオフィス自身のアクセスリスト** — reasoningEngine 上の `:getIamPolicy`（§5）。これは短く、意図的なリストである：**このエージェントに特に** アクセスが与えられているのは誰か。悪意のあるアカウントを指名していることを予期すること。
  2. **プロジェクトレベルのリスト** — **`aiplatform.reasoningEngines.query`** を含むロールを持つ各プリンシパル（そしてそのついでに §1 の 2 つのバイパス権限も確認すること）。これは長く、偶発的なリストである。**実際に見つけたものを数え**、ロールを逐語的に引用すること。**viewer** という名前のロールがそこに現れることを声に出して指摘すること — それはどんな説明よりもうまく要点を伝える。
  3. **実際に他に誰がそれを呼び出しているか** — バックオフィスへの **直接の** ルートを探して、ストアの構成／挙動を確認する。見つけたら、それを名指しすること：フロントデスクを経由せず、owner レベルの ID の下でバックオフィスと会話しているアプリケーション。
- **それから、悪意のある呼び出しを本当に行う**（§5）：シードされた鍵を取得し、**自分自身の資格情報を決して変えてしまわないよう、隔離された gcloud 構成で**（§8）トークンを生成し、バックオフィスへ A2A `message:send` を POST する。実際に受け取った **HTTP ステータスコード** と **応答本文** を引用すること。
- **良い状態はどう見えるか — 固定の形式、ライブの出力だけで埋める：**

  ```
  | 誰 | アクセスの出所（リソースポリシー / プロジェクトロール） | 何のコマンドがそれを示したか | それによって何ができるか | そうあるべきか？ |
  ```

  **「何のコマンドがそれを示したか」のセルは必須であり、装飾ではない** — それは、図が従うのと同じ来歴（provenance）のルールを、実際に読み取る対象の面に適用したものである。**来歴のセルが空である行は、発見事項ではなく主張であり、そこには入らない。** ストアの直接ルートは、まさにこれが存在する理由である：ある実際の実行では、この表の中で **どこにも背後にコマンドがないまま** 3 回主張された一方で、その隣の図は同じルートを未検証として正しく描いていた。テキストと図が互いに矛盾しており、そしてその主張は結果的に **真** であった — それこそがそれを危険にするものである。なぜなら、応答の中にそれを当て推量と区別するものが何もなかったからである。

  **他に何を見つけたかにかかわらず、必須の行が 1 つある：プロジェクトレベルの保有者。** その 「誰」のセルは、あなたが実際にプロジェクトポリシーから読んだロールを — そこにあれば `viewer` も含めて — 名指しし、その来歴のセルは、それらを生み出した §5 のコマンドを名指しする。⛔ **その行を、名指しされた単一の呼び出し元ではないからといって省略しないこと** — それはリスト中で最大のグループであり、ステップ 4 における正直な主張が、整った主張よりも狭くなる理由である。

  その上に、平易な言葉での見出し（*「あなたの機密のマージンロジックは、それを決して持つべきでなかったログインに応答してしまう — これが私が今行った呼び出しであり、返ってきたものである」*）、そしてリーダーの言葉で、見逃しようのない区別を置く：
  > **「データを読める」と「エージェントを呼び出せる」は、2 つの異なる権限である。** M1 は前者を修正した。これは後者であり、ここでは何一つそれを統べたことがない：バックオフィスへのアクセスは、意図的なリストであったことは一度もなく — プロジェクトレベルで配られたロールの副作用である。
  それから、残っているギャップを **それを閉じるものを名指しせずに** 見えるままにしておく：この呼び出し元リストを選んだ者は誰もいない — それは別の理由で行われた付与の残滓であり、誰も選ばなかったリストは、誰も反対しないであろうリストと同じものではない。⛔ **決して、次のステップの問いを求めて締めくくらないこと。** ある実際の実行では、その習慣が 6 つの応答を連続して予告してしまった；このステップの下の方にある締めくくりの注記が優先する。
- **この図 — ここでは必須であり、CALL 図である（§2）。** モジュール全体が軸とする唯一の区別を描く：誰がバックオフィス **自身の** 呼び出し元リストにいて、誰が **そこにいないまま** 入ってくるか。**実線の矢印はちょうど 1 本だけ** — あなたが実際に行った悪意のある呼び出しであり、それがこのステップが行う唯一の呼び出しである。**他のすべての矢印は破線** である。なぜなら、ポリシー上の権限を読んだだけで、誰かがそれを使うのを見てはいないからである。それらを実線で描けば、見てもいない呼び出しを主張してしまったことになる：

  ```
  今 [Markdown Strategy] に到達できるのは誰か、たった今読み取ったもの

    バックオフィス自身の呼び出し元リストにいる:
      (test-agent-caller) --> [Markdown Strategy]   たった今それを呼び出した

    そのリストにはいないが、そこに到達できる権限を持つ:
      [Price Match] --?--> [Markdown Strategy]   呼び出せる
      [store portal] --?--> [Markdown Strategy]   呼び出せる、直接
      (11 のプロジェクトロール保有者) --?--> [ここのどのエージェントも]  呼び出せる

    破線 = ポリシーで読み取った権限であって、このステップで誰かが行った
    呼び出しではない。各々を解決するもの: 呼び出しを行う、状態を読む。
  ```

  **`11` は、あなたがライブのプロジェクトポリシーで数えた数が何であれ、そのプレースホルダーである** — このファイルから引きずってきた数字でも、§1 の「10」という語でも決してない。2 つのグループが要点である：2 番目のものこそ、正直な主張が整った主張より狭くなる理由であり、それをここで描くことこそが、ステップ 3 やステップ 4 で整った主張を書いてしまうのを防ぐものである。あなたが実際に読んでいないものはすべて、それを解決するコマンドを名指しする行を添えた `?` として描く — あなたが省略したグループは「そこには誰もいない」と読まれ、それはあなたが裏付けられない主張である。ストアの直接ルートが存在しないと分かった場合は、その行を省略し、その理由を述べること；見つけていないルートを描いてはならない。

  ⛔ **ここで破線の矢印を実線に格上げしないこと。ルートがどれほど自明に見えようとも。** フロントデスクがバックオフィスに到達できるという能力は、**あなたが今読んだばかりのポリシーからの推論** である — プロジェクトポリシーは、それが呼び出し権限を伴うロールを持っていることを示している — そして推論は観察ではない。ステップ 4 が、フロントデスクを本当に行使する最初のステップであり、それ自身の before/after を伴う。ストアポータルの線はさらに弱い：それはアプリケーション自身の構成に由来し、その構成は **古いハードコードされたエンジン ID** を持つことが知られている（§8）。だからそれを破線で描き、凡例でどこで読んだかを述べること。ある矢印をどのコマンドが生み出したか言えないなら、その矢印は入らない — **そして同じルールが、その上にある表を統べる**：「何のコマンドがそれを示したか」 のセルが空である行は、発見事項ではなく主張であり、それも入らない。図とテキストは、単一の基準に従う。
- **誤ってラベル付けしない：**
  - **あなたが行わなかった呼び出しは、発見事項ではない。** 悪意のある呼び出しを、行わずに記述すれば、そのステップを捏造したことになる — そして、起きたことしか繰り返せないステップ 4 を破壊したことになる。
  - **ステップ 1 での 403 は結果であって、解決すべき失敗ではない。** 悪意のある呼び出しが実際の応答を返さ *ない* 場合は、はっきりとそう述べ、他の何よりも先に事前状態の整合性の結果を確認すること。**200 が得られるまでリクエストを変え続け、それを「before」と呼ぶことは決してしないこと。**
  - **2 つのリストを混同しないこと。** 「エージェント上の 1 つのバインディング」と「プロジェクトレベルの 10 のプリンシパル」は、異なるコマンドからの異なる文である。それぞれがどのコマンドに由来するかを述べること。
  - ⛔ **検証が完了しなかったなら、あなたは数字を持っていない。** §5 のシーケンスは 2 つの計数を出力し、その後にプリンシパルのリストを出力する；その 3 つのいずれかが終わらなかった場合は、検証が不完全であると報告し、何が欠けているかを述べる。**停止する前にスクロールしていった行から合計を推測することは決してせず**、部分的な読み取りを自信ありげな数値に丸めることも決してしないこと。ある実際の実行では、計数がループの途中で中断されたにもかかわらず、その数字がリーダーに **6 回** 宣言された — それはこのモジュールの正直なスコープの主張の、基盤となる半分であるため、測定されていない計数は、これ以降の各ステップの締めくくりを毒する。
  - ⛔ **ロールの計数は、呼び出し元の計数ではない。** それらは異なる母集団であり、リーダーが尋ねたのは 2 番目の方である。数値を引用する前にプリンシパルを解決し（§5）、あなたが述べるどの数字も 2 つのうちのどちらに属するかを述べること。
  - **ゲートウェイをまだコントロールと呼ばないこと。** ステップ 1 では、それは何にもアタッチされておらず、何も適用していない。それはステップ 3 で、しかも判定を読み返した後にのみ、コントロールになる（§1、§7）。
  - **解決策をまだ提案しないこと。** ここでブロック、ロール、あるいは PMA のプリンシパルを名指しすることは、ステップ 2 を台無しにする。
  - **悪意のあるアカウントの秘密鍵を決して出力せず、終わったらローカルのコピーを削除すること**（§8）。
- **どう締めくくるか — 毎回導き直す形式であって、決して復唱する 1 行ではない。** このステップがリーダーに実際に教えたこと：バックオフィス自身の許可された呼び出し元リストには 1 つの名前が入っており、それは持ち主のいない余分なログインで、たった今あなたに応答したもの、そして企業が本当に依存している呼び出し元はそのリストにまったく入っていない — したがって、フロントデスクが入ってくる経路が何であれ、それはこことは別の場所で付与されたのである。正直な締めくくりは *それ* に着地するのであって、次にすべきことに着地するのではない。**論点** を、あなた自身の読み取りが裏付ける任意の順序で：
  - リストにある唯一の名前は、そこにあるべきではない；
  - 企業が依存している唯一の呼び出し元は、リストに入っていない；
  - したがって、フロントデスクを受け入れているものが何であれ、それはこのリストではない別の場所で付与された；
  - ゆえに、アクセスを制御しているのはこのリストではない。

  **別の** 資産環境からの、和集合を示すための（そしてコピーするためではない）作り込んだ例：*「給与エクスポートの許可リストにある唯一のユーザーは、稼働していないバッチジョブであり、そのエクスポートを毎月引き出す財務部門は、そこに入っていない。だから財務部門は別の何らかの方法で入ってきており、このリストはコントロールというよりドキュメントである。」* ⛔ **その言葉を再利用しないこと。** NovaSmart には給与エクスポートも財務チームもない；この例は、ここにコピーできる文が 1 つもないように、わざと噛み合わないように作られている。

  このターンに返ってきたものから、あなた自身のバージョンを導き直すこと；あなたのライブの読み取りが異なる姿を示したなら、言葉は変わる。それから、そのギャップから 2 つか 3 つの問いが育つ — マージンロジックを持つシステムにおいて呼び出し元リストはどう見えるべきか、誰がそこに自分の名前を載せるのか、新しい名前がそこに現れたことに NovaSmart はどうやって気づくのか。⛔ **決して、ブロックが何を壊すかを尋ねて締めくくらないこと。** それは次のステップのリクエストとほぼ一語一句同じであり、それで締めくくることは、ステップゲートに関する警告が描写する、まさにその予告である。⛔ ブロックに値札を付けず、ルートを計画として列挙せず、解決策を名指ししないこと — それは次のステップ自身の報告である。

### ステップ 2 · それをブロックするのに何がかかるかを見る — ⛔ 読み取り専用、判断の瞬間

> **このステップは何も変更しない。** あなたは影響をモデル化しているのであって、適用しているのではない。あなたが「〜だろう」と記述するものはすべて、ステップ 3 まで「〜だろう」のままにとどまる。

- **どこを見るか（すべて読み取り）：** ステップ 1 と同じ 2 つのリスト、加えて — 見つけた各呼び出し元について — バックオフィスを実際に何に使っているか。リーダーがした問いは *「何が壊れるか？」* なので、それに呼び出し元ごとに答えること。
- **分析を、リーダーの言葉で：**
  - **フロントデスク（PMA）：** それは想定された呼び出し元である；それをリストに名指しすることが要点のすべてである。動作し続ける。
  - **悪意のあるログイン（`test-agent-caller`）：** その **唯一の** アクセスは、このエージェント上のバインディングである。それを取り除けば、何も残らない — **それが実際に変わる唯一のものである**。
  - **ストアの直接ルート：** **動作し続ける** — そしてこれが居心地の悪い部分である — なぜなら、それはアクセスが **プロジェクト** に由来する **owner レベル** のアカウントとして実行されており、エージェント自身のリストに由来するのではないからである。**これを発見事項として述べること、安心材料としてではなく：** このエージェント自身のポリシーに対してあなたが何をしようとも、すでにプロジェクトの owner である呼び出し元を止めることはできない。
  - **より広範なプロジェクトレベルの保有者：** 同様に影響を受けない。**これが平易な言葉でのルール C である** — 一度だけ、はっきりと言うこと：*「このエージェント自身のリストをブロックしても、消えるのは **このエージェント上で** 付与されたアクセスだけである。プロジェクト全体で誰かに付与されたアクセスを取り除くことはできない。」*
- **良い状態はどう見えるか — 固定の形式、ライブの出力だけで埋める：**

  ```
  | 呼び出し元 | 今日どうやって入ってくるか | フロントデスクだけに制限した後 | 壊れるか？ |
  ```

  そして正直な要約：このブロックは **安全である** — それが消す唯一の呼び出し元は、そこに決しているべきでなかったものである — **そして部分的である**、先の理由により。
- **判断のための問いで終え、そこで止まる：** *プロジェクトレベルのロールが依然としてその脇を通り抜けられるとき、エージェント自身に意図的なリストを置くことで十分なのか？* リーダーに答えさせること。あなたの判定を前もって出力せず、何も適用せず、そして — 同様に — **承認を求めないこと**（§0）。
- **誤ってラベル付けしない：**
  - **これは予測であって、結果ではない。** それを仮定法で記述すること。「悪意のあるエージェントは今や拒否されている」と書いている自分に気づいたら、2 つのステップを飛ばしてしまっている。
  - **黙って計画を広げないこと。** 「ついでに、プロジェクトレベルの付与も削除すべきだ」は境界の外であり、エージェント自身のモデルへのアクセスを壊してしまう（§3）。それを未対応の作業として名指しすること。
  - **話を整った状態に保つために、ストアの発見事項を過小評価しないこと。** アプリケーションが owner としてバックオフィスに直接到達していることは、まさにセキュリティのリーダーが聞く必要のあることである。
  - 「反対がなければこれを適用します」と言わないこと — それは承認フィルタであり、禁じられている。
- **どう締めくくるか — 毎回導き直す形式であって、決して復唱する 1 行ではない。** 先の判断のための問いが、このステップの指定された終わりであり、それは維持される。その *周り* に来るのは、あなた自身の影響評価の表の正直な含意である：企業が依存しているものは何一つ、問題の扉を通じては動いておらず、その扉はいくつかあるうちの 1 つである。**論点**：
  - 企業が依存しているものは何一つ、閉じられようとしている扉を通じては動いておらず、その部分はきれいである；
  - その扉はいくつかあるうちの 1 つであり、他の扉はそれとは無関係に開いたままである；
  - ゆえに、これ以降にこれについて言われることは何であれ、非常に注意深く言葉を選ばねばならない。

  **別の** 資産環境からの、和集合を示すための（そしてコピーするためではない）作り込んだ例：*「撤去された端末のためにクリニックの記録システムを閉じても、誰にも何のコストもかからない — しかし同じ記録は、スコープに一度も入っていなかった他の 2 つのシステムから到達可能であるため、『記録はブロックされている』は私が裏付けられない文になるだろう。」* ⛔ **その言葉を再利用しないこと。** NovaSmart にはクリニックも端末もない；この例は、ここにコピーできる文が 1 つもないように、わざと噛み合わないように作られている。

  **「いくつか」とは、あなた自身の表が数えた数が何であれそれであり**、このファイルの数字ではない；ルートを 3 つ見つけたなら 3 つ、5 つなら 5 つと言うこと。「非常に注意深く言葉を選ぶ」は、ここで本物の仕事をしている — それは、リーダーがそれを必要とする立場になる前に、モジュールが必要とする正直さの規律を、たった 1 つのアクションも名指しせずに植え付ける。⛔ リーダーの代わりに判断のための問いに答えず、承認を求めず、締めくくりが、ブロックが *どのように* 適用されるか、どのロールを使うか、どのプリンシパルを名指しするか、へと逸れていくのを許さないこと。

### ステップ 3 · フロントデスクのためにそれをブロックする — 唯一のミューテーション

- **このモジュールは 2 つの問いに答え、それらは 2 つの異なるコントロールを必要とする。** *「誰がバックオフィスを呼び出せるか？」* は、バックオフィスエージェント上のアクセスリストによって答えられる — それがこのステップの残りであり、変更なしのまま維持される。*「バックオフィス自身はどの宛先に到達できるか？」* は、次に述べる **Agent Gateway** によって答えられる。⛔ **どちらも他方の代用にはならない。** それらを順番に行い、別々に報告し、一方を他方をカバーするものとして決して提示しないこと。

#### ステップ 3b · バックオフィスをゲートウェイの背後に置く — どの扉を越えられるか

- **エグレスゲートウェイを Markdown Strategy Agent にアタッチする（§5）。** ⚠️ エージェントはすでに `identity_type: AGENT_IDENTITY` を持っていなければならない — `400 FAILED_PRECONDITION` はそれを持っていないことを意味し、それは M1 の仕事であって、ここで修正するものではない。
- ⛔ **ゲートウェイは認可ポリシーを必要とし、それがなければ すべてを拒否してしまう** — エージェント自身のモデル呼び出しを含めて。するとエージェントはリクエストを受け付けても何も返さず、ブロックされたエージェントではなく壊れたエージェントのように見える。**何かを判断する前に、IAP 認可拡張と、そのゲートウェイを対象とする認可ポリシーを作成すること**（§5、§8）。
- **`roles/iap.egressor` を レジストリ全体（REGISTRY-WIDE）で付与する。リソース単位ではない。** レジストリ全体であれば、エージェントは動作し続けられる；リソース単位の付与では、他のあらゆる宛先が — モデルを含めて — 拒否されたままになる。
- **次に、このモジュールが扱う単一の宛先を拒否する**。`hosts: [bigquery.googleapis.com]` と `action: DENY` を名指しする認可ポリシーで。
- ⛔ **ここで MCP の *メソッド* によってフィルタリングすることはできない。** ゲートウェイは BigQuery ホストへの不透明なリクエストを見るのであって、その中の JSON-RPC 本文を読むことはできない。したがって「読み取りを許可し、書き込みを拒否する」ことは、この層では **達成できない** — 認可ポリシーの `mcp.methods` 形式も、IAM 条件の `mcp.method` 形式も試されたが、どちらも一致しない。**それを試みてこのモジュールを費やさないこと。** 読み取り／書き込みの区別は次のサブステップに属し、そうでないと言うことは、あなたが証拠づけられない主張である。
- **長い沈黙を予期すること。** アタッチはおよそ **4 分** の長時間実行オペレーションであり、その後 IAM が伝播するのに約 **90 秒** かかる。**終端状態までポーリングし、リソースを読み直すこと** — 戻ってきたコマンドは適用された変更ではなく、早すぎるタイミングで取った読み取りは *変更前* の値を返す。
- **良い状態はどう見えるか：** ゲートウェイ自身の判定を引用する — 宛先 URL に対する `ALLOWED;DENIED` — に加えて、エージェントの `principal://` を名指しする IAP の決定。⛔ **エージェント自身の応答ではない**（§7）。

#### ステップ 3c · そこで何を できる かを削減する — 読み取りは可、書き込みは不可

- ⚠️ **ゲートウェイはこの半分を行えず、ステップ 3b の判定はそれをカバーしない。** ゲートウェイの許可は、バックオフィスが BigQuery に *到達できる* ことを意味する；そこで何かを *変更できる* かどうかについては何も言わない。今日は変更できる：Markdown Strategy Agent は **プロジェクトレベルの `roles/bigquery.admin`** を持ち、SQL のミューテーションを試みるよう指示されている。**このサブステップが着地するまで、書き込みは成功する。**
- **ゲートウェイではなく、エージェント自身の ID を削減する。** エージェントの `principal://` からプロジェクトレベルの `roles/bigquery.admin` を取り除き、その仕事が必要とするものだけを返す：プロジェクトレベルの **ジョブ実行ロール** に加えて、実際に使う 2 つのデータセット上の **データセットに限定した読み取り**（§5）。
- ⛔ **両方の半分を行うこと。さもなければエージェントが立ち往生する。** ジョブ実行ロールは、クエリを *実行する* 権利を付与するが、**データへのアクセスはまったく付与しない**。データセットの読み取りを追加せずに管理者ロールを取り除くと、エージェントはもはや自分の仕事ができなくなる — しかもそれをはっきりとは言わず、記憶から応答する（§7）。
- **なぜこれが正しい層なのかを述べること。** ゲートウェイは *宛先* を統べ、リクエストの中を見ることはできない；データプラットフォームは *動詞* を統べ、見ることができる。2 つのコントロール、2 つの問い、そしてリーダーは両方を聞かねばならない。
- **良い状態はどう見えるか：** 同じエージェントが、同じ分に、**テーブルの一覧表示に成功し、そのうちの 1 つの更新に失敗する** — その失敗が、エージェントが言ったことによってではなく、**データから** 確認される（§7）。


- **PMA のプリンシパルを、記憶からではなく、デプロイ済みのエージェントから解決する（§5）。** それは、**プロジェクト番号**、**リージョン**、**PMA のエンジン ID** から構築される SPIFFE スタイルの値 `principal://…` である。誤る方法が 2 つあり、どちらも無言である：信頼ドメインを自分で組み立てること、そして読み取った値がすでに `principal://` スキームを持っているのに、それを **重複させる、または省略すること**（§8）。それを読み、出力し、正確な文字列を使うこと。
- **BEFORE のポリシーとその `etag` を取得する。** あなたの復元手段は「私が記録したものを復元する」であり、`etag` こそがあなたの書き込みを安全にするものである：それは API に「ポリシーが私の読んだものと同じままである場合にのみ、これを適用せよ」と伝える。それなしで書き込めば、今そこにあるものが何であれ、それを盲目的に上書きしていることになる。
- **限定的な置換を書き込む。** 読み取ったポリシーを取り、呼び出しロールの `members` **だけ** を唯一の PMA プリンシパルに変え、他のすべてのバインディングをそのまま残し、`etag` を保持して `:setIamPolicy` に `POST` する（§5）。**`setIamPolicy` はドキュメント全体を置き換える。** `bindings` 配列を、ゼロからではなく **読み取ったものから** 構築すること。
- **ロールの選択 — 何を選び、なぜ選んだかを述べること：**
  - **`roles/aiplatform.user`** は、`aiplatform.reasoningEngines.query` を含む、文書化されたロールであり、この資産環境がこのリソースですでに使っているものである。**リソース上で** バインドすれば、それは擁護できる選択である — **そしてそれは「このエージェントを呼び出せる」よりも広い** ので、そう述べること。
  - ❌ **`roles/aiplatform.reasoningEngineUser` は存在しない。** 決してそれを提案しないこと（§1）。

  ⛔ **その最後の約束は、果たせる場合にのみすること。** それはステップ 4 で満期を迎える負債であり、そこでは §5 のプリンシパルが **1 行に 1 つずつ、出力** されねばならない。§5 の解決が完了しなかった場合は、作り出せないリストを約束するのではなく、ここでそう述べること — 果たされない約束は、リーダーにとっては与えられた答えのように読まれる。そしてある実際の実行では、そのせいで彼らはモジュール全体を通じて、**自分自身のラボの人間のログイン** がそこに入っていたことに気づかずに終わったのである。
- **この図 — ここでは必須であり、CALL における BEFORE/AFTER である（§2）。** 両方の半分は、あなたが読んだポリシーに由来する：BEFORE はこのステップの冒頭で取得したドキュメントから、AFTER は **読み直した** `:getIamPolicy` からであり、書き込み自身の応答からではない。**3 番目のブロックは任意ではなく、下に留め付けられた警告でもない — それは図の内側に入る：**

- **誤ってラベル付けしない：**
  - **成功した `setIamPolicy` は、ブロックされたエージェントではない。** `:getIamPolicy` の読み直しを引用すること（§7）。
  - **適用することは実証することではない。** ステップ 4 が 403 を所有し、その言葉はステップゲートの管理下にある（§2）。
  - **排他性を主張しないこと。** 「Price Match だけがそれを呼び出せる」は、あなたがそれを書いた瞬間に偽である（§0 ルール C）。許される文は §1 と §4 · ステップ 4 にある。
  - **ついでに他のバインディングを整理しないこと。** 読み取ったポリシーが呼び出しロールを超えるバインディングを含んでいる場合は、それらを保ち、言及すること — 「ドキュメントを開いていた」を、片付けてよい許可として扱わないこと。

- **どう締めくくるか — 毎回導き直す形式であって、決して復唱する 1 行ではない。** あなたは構成を変更し、それを読み直した。それが今この瞬間にあなたに利用できる真実の全体であり、締めくくりはまさにそこに位置しなければならない。**論点**：
  - リストは今や 1 つの呼び出し元を名指ししており、それが構成の言っていることである；
  - 構成とは、未来についての主張である；
  - まだ、いかなる実際のリクエストもこれを確認も反証もしていない。

  **別の** 資産環境からの、和集合を示すための（そしてコピーするためではない）作り込んだ例：*「配送エージェントのアカウントは倉庫システムのリストから外れており、リストは意図されたとおり正確に読める。私が持っているのは書かれた意図である；私がそれを変えて以来、その扉には何も触れていない。」* ⛔ **その言葉を再利用しないこと。** NovaSmart には配送エージェントも倉庫システムもない；この例は、ここにコピーできる文が 1 つもないように、わざと噛み合わないように作られている。

  それらの論点に着地することは、証拠について正直であり、*しかも* このモジュールが警告する伝播の遅延を、それを名指しせずに静かにカバーする。⛔ 締めくくりでは、**テストする、試みる、繰り返す、実証する、検証する、ブロックされた、拒絶された、拒否された** という語は、一切現れてはならない — それらのどれもが、次のステップの結果を宣言するか、あるいはリーダーに次のステップの指示を手渡してしまう。⛔ 悪意のある呼び出し元が締め出されたとは言わないこと；それをまだ尋ねられていない。問いは、書かれたリストと観察された結果とのギャップから育つ：構成が実際に有効であることの証拠として NovaSmart は何を受け入れるのか、そして企業はその差とどれだけの間、共存できるのか。

### ステップ 4 · 悪意のある呼び出し元が締め出されたことを実証する

> **🔒 ステップ 4 の管理 — 3 つの厳格な要件、いかなる主張があなたの口から出る *前に* すべて満たすこと：**
>
> 1. **このセッションで、ステップ 1 のバイト単位で同一の悪意のある呼び出しを もう一度行った 状態でなければならない** — 同じ URL、同じ本文、同じ ID、**新しく生成したトークン**。**再呼び出しなし → 主張なし。** 記憶された「before」を、言い換えた「after」と比較しても、それは before/after ではない。
> 2. **肯定的な主張としては、「ブロックされた」「証明」「実証する」「実証された」「検証済み」という語は禁止される**。ただし、**実際の応答またはログエントリが同じターン内で引用される** 場合を除く — HTTP ステータス行とエラー本文、あるいは監査エントリ。「今や拒否されているはずだ」はいけない。ポリシーからの推論もいけない。
> 3. **正当な ルートも行使した状態でなければならない** — **Price Match Agent** を通じた、10% を超える割引の本物のエスカレーション — そして本物のマージン判定が返ってきたことを示していなければならない。有用性の観点で一度もテストしていないブロックは、リーダーが求めた結果ではない。**あなたが引用する競合価格は、シードされた競合テーブルが実際に記載しているものでなければならない**（§5）：フロントデスクは割引を見る *前に* リストを検証するため、でっち上げた価格は誤った理由で拒否され、あなたのブロックについて何も教えてくれない。
>
> **再実行が拒否を返さない場合** — 200 が得られる、または曖昧な 400/404 が得られる — **唯一** の正しい出口は、何を送ったか、何が返ってきたか、次に何が必要かを述べることである（IAM の伝播を待って一度だけ再試行する · `:getIamPolicy` を読み直して、あなたの書き込みが実際に適用されたことを確認する · URL と API バージョンがステップ 1 の呼び出しとバイト単位で同一であることを確認する · ステップ 1 の事前整合性チェックがきれいであったことを確認する）。行を **未検証** と印付けること。**400 や 404 を 403 として決して提示しないこと** — 不正な形式のリクエストと拒否されたリクエストは異なるイベントであり、そのうちあなたの証拠となるのは一方だけである。

- **何かを結論づける前に、IAM の伝播を待つこと。** IAM の変更は通常 **約 2 分** かかり、**7 分以上** かかることもある；すでに発行されたトークンはさらに長く有効な場合がある。早すぎる「まだ入ってしまった」は同期のアーティファクトであって、結果ではない — そしてそれを失敗として報告することは、未検証のブロックを成功として報告するのと同じくらい誤りである。**何かを書く前に、一度だけ再試行すること。**
- **どこを見るか — 確度の高い順に：**
  1. **あなた自身が、悪意のあるトークンで行った呼び出し** — HTTP ステータスとエラー本文。**これがこのモジュールで最も確かな証拠である**。なぜなら、あなたがそれを引き起こし、プラットフォームがそれを拒否するのを見て、UTC タイムスタンプ付きで逐語的に引用できるからである。
  2. **バックオフィスエージェント上で読み直した `:getIamPolicy`** — これは **構成** の証拠である：あなたが意図したアクセスリストを示すのであって、誰かが止められたことを示すのでは **ない**。それを構成としてラベル付けすること。
  3. **拒否された呼び出しについての監査ログのエントリ**（`status.code=7`、§5） — 裏付けである。データアクセス監査がこの面を捕捉していない場合、それは **存在しないことがある**；ここでの不在は (1) の反例では **なく**、また (1) の代用でも **ない**。どちらを持っているかを述べること。
  4. **ストアのレンダリングされた応答** — ❌ **どちらの方向にも証拠ではない。** それは、実際の応答が短いか空のときにもっともらしい応答をでっち上げ、しかも **owner** としてバックオフィスを呼び出す。
  5. **モニタリングのダッシュボード** — ❌ **証拠ではない。** それはログ内のテキストの一致を探すことで結果を主張する。
- **正当なルートを、フロントデスク（FRONT DESK）を通じてテストすること、バイパス（bypass）を通じてではなく。** これはステップ 4 を誤る最も簡単な 2 つの方法のうちの 1 つである：ストアには **バックオフィスを直接** 呼び出すルートがある。*それ* を行使して「エスカレーションはまだ機能する」と報告することは、**バイパス** を証明する — それはプロジェクトレベルの owner ゆえに機能する — のであって、PMA→MSA については何も教えてくれない。**Price Match Agent に、10% を超える本物の割引リクエストを送り**、データが実際に記載している競合価格を引用し（次の項目 — これは任意ではない）、返ってきたマージン判定を示すこと。PMA→MSA のジャンプそのものを観察できない場合は、まさにそう述べること：フロントデスクは本物の判定を返した、そしてこれがあなたが独立して確認できなかったことである。
- **⚠️ あなたが引用する価格は、シードされた競合データに由来しなければならない — これはステップ 4 を誤るもう 1 つの簡単な方法であり、最も起こりやすいものである。** フロントデスクは、あなたの数字について推論 **しない**。それは、競合価格を競合テーブルに対して **完全一致** で照合する検索ツールを呼び出し、一致しなければ `NOT_FOUND` を返す — それをフロントデスク自身の指示は、**割引ルールが参照される前に到達する、決定的な拒否** として扱う。したがって、あなたがでっち上げたもっともらしく見える価格は、M2 とは何の関係もない理由で拒否される。**資産環境が実際に持っているペアを使うか、まずライブで 1 つ解決すること（§5）：**
  > **SKU-HSE-4001** · 定価 **$349.00** · 競合 **BetaBuy** が **$296.65** — ちょうど **15%** であり、これは 10% の上限を超えてエスカレーションを強制する。

  そのデータについては、数字を「盛って良く見せ」ないよう、2 つの事実を覚えておく価値がある。第 1 に、各製品は **同じ 2 段階のスケール** でシードされている — 定価より 5% 下の競合が 1 つ、15% 下が 1 つ — したがって **15% がこの資産環境のどこであれ利用可能な最も深い割引である**；「20% の割引」はどの製品に対しても検証できない。第 2 に、この品目のもう 1 つのリスト（**AlphaStore が $331.55**）はちょうど **5%** であり、それは上限を *下回って* おり、バックオフィスに到達することなくフロントデスクで承認される — したがってここでは何も証明しない。⛔ **丸めず、リアリティのために調整せず、実行ログやこのラボの歴史から価格を持ってこないこと** — `$300.00` という数値がここで出回ったことがあるが、それはシードされたどの行とも一致しない。
- **良い状態はどう見えるか：** このモジュールの唯一の検証形式 — **3 列、それ以外なし、§9 が宣言するのと同じもの** — で、各 「結果」のセルには、引用されたステータス／本文、あるいは **未検証** という語が入る：

  ```
  | 検証項目 | どう検証したか | 結果 |
  ```

  **これは、どのステップであれ、M2 が検証に使う唯一の表形式である。** ここでは 2 つの行が必須である：**バイト単位で同一の悪意のある再実行** と **フロントデスクのエスカレーション**。before/after はセルの *内側* に住むのであって、余分な列にではない — ステップ 1 の結果と正確な呼び出しを **どう検証したか**に置き（*「ステップ 1 の呼び出しを、新しいトークンでバイト単位でそのまま繰り返した；ステップ 1 は 14:09 UTC に 200 を返していた」*）、あなたが今観察したステータスを **結果**に置く。実際に実行した他の何かがあれば、その行を追加する；実行していない行は削除する。

  次に来るのが **正直な最終行** であり、それはあなたがこのモジュールで書く最も重要な一文である：

  | ❌ 禁止（偽） | ✅ 許可（真であり実証可能） |
  | :-- | :-- |
  | 「Price Match だけがバックオフィスを呼び出せる。」 | 「悪意のある呼び出し元は拒否される — これがその 403 である — そしてバックオフィス自身のアクセスリストは、これでちょうど 1 つの承認された呼び出し元を名指ししている。」 |
  | 「他の全員は締め出された。」／「バックオフィスは非公開である。」 | 「**このエージェント上で** 付与されたアクセスは、今や意図的な 1 名だけのリストである。**プロジェクト全体で** 付与されたアクセスは変わっていない：*N* のプリンシパルが、いまだにエージェントの呼び出しを含むロールを持っている — これがそれらである。」 |
  | 「接続は制御されている。」 | 「1 つの接続が、今や明示的な許可リストによって統べられている。それを迂回できるプロジェクトレベルの付与が、次に取り組むべき作業である。」 |

  ⛔ **「これがそれらである」は、リストが約束されているのではなく、出力されていることを意味する。** 2 番目の行の許される文はコロンで終わり、それに続くのは `/tmp/invoker_members.txt`（§5）の実際のプリンシパルである — 1 行に 1 つ、逐語的に、省略記号なし、「その他」なし。**その文を書いておいてリストを出力しなければ、あなたは禁止された文をより丁寧な言葉遣いで書いたことになる。** 同じことが、ステップ 3 の正直な警告 — *「誰がそうかを正確にお見せする」* — にも当てはまる：それは負債であり、ここがその満期である。ある実際の実行では、約束がなされ、数字が与えられ、リストは一度も示されなかった — そしてリーダーは、**自分自身のラボの人間のログイン** がそこに入っていたことを一度も知らされなかった。それはこのモジュールが言うべき最も説得力のあることである。⛔ **プリンシパルを解決できなかった場合は、リストが利用できないこととその理由を述べること** — 約束をしておいて、それを黙って省略してはならない。

- **残された作業を名指しし、その仕組みを正直に名指しすること。** ギャップは、**プロジェクトレベルの `aiplatform.*` 付与を、各プリンシパルが実際に必要とするものへと削ること** によって閉じられる（慎重に — それらの付与はエージェントのモデルへのアクセスも伴う、§3）。ここでは拒否（deny）ポリシーは是正策として利用 できない ことに注意すること — deny はプロジェクト／フォルダ／組織レベルにのみ付与でき、`reasoningEngines` はそれを限定するために必要なリソースタグをサポートしていないため、拒否はすべてのエージェントに影響してしまう。それを推奨しないこと。残る保守作業は付与の削減であり、それは許可の付与を *打ち消せる* 唯一の種類のポリシーである。**それらを推奨事項として名指しすること。どちらもここで構築しないこと**（§3）。
- **誤ってラベル付けしない（ここが、自信ありげに見える応答が誤りに転じる場所である）：**
  - **404 は 403 ではなく、400 も 403 ではない。** ステータスコードとメッセージを確認すること。誤ったエンジン ID や誤った API バージョンは、あなたのポリシーとは何の関係もない拒否を生み出す。
  - **1 人のメンバーを名指しするリソースポリシーは、呼び出し元が 1 つだけ残っていることの証明ではない。** それはリストが言っていることの証明である。両者が食い違う理由がルール C である。
  - **バックオフィスからの空の、あるいは役に立たない応答は、拒否ではない。** ステータスを引用すること。
  - **欠けている監査エントリは、拒否でも承認でもない。** 待って、一度だけ再試行し、それから **未検証** と印付けること。
  - **⚠️ フロントデスクからの「検証済みの競合リストがない」を理由とする DENIED は、失敗したブロックではなく 欠陥のあるテスト である — そしてそれは、このステップで起こりうる最も誤解を招くことである。** エスカレーションの応答が、競合リストを検証できなかったという理由でリクエストを拒否した場合、あるいは自分が *知っている* 競合リストを列挙して返ってきた場合、それはフロントデスクの検索が `NOT_FOUND` を返してそこで停止したということである — **割引ルールには決して到達しておらず、したがってバックオフィスを呼び出そうと試みたことすら一度もない。** それは、M2 が統べる接続よりも手前の、あなたのリクエストにおける **データ** の不一致である。**それはこのモジュールの承認でも失敗でもなく、そのどちらとしても報告してはならない。** 競合テーブルが実際に記載している価格（上記）で再実行し、2 番目の結果だけを報告すること。⛔ とりわけ、**それを「ブロックがエスカレーションを壊した」と語らないこと** — リーダーは、ビジネスを壊すブロックは勝利ではないと言われたばかりなので、その文は確認された自傷的な中断のように受け取られ、しかもそれは偽であろう：フロントデスクは、あなたのポリシーが名指しする唯一の呼び出し元であり、かつプロジェクトレベルのロールも持っているため、そのジャンプは二重に許可されている。記載された価格での再実行が *それでも* 拒否する場合は、何を送ったかを述べ、応答を引用し、行を **未検証** と印付けること。
  - **誤った原因に帰さないこと。** ステップ 1 の事前検証がきれいであったなら、403 はあなたの変更に帰属できる；きれいでなかったなら、帰属は不確かであることとその理由を述べること。
  - **生の出力に含まれていなかったロール名、プリンシパル、ステータスコード、タイムスタンプ、エンジン ID を決して書かないこと。**
- **どう締めくくるか — 毎回導き直す形式であって、決して復唱する 1 行ではない。** これはこのモジュールで最も確かな証拠であり、それゆえ主張を誇張しやすい最たる場所である。あなたが達成したことの **規模** において締めくくること、その全体においてではなく。**論点**：
  - 資産環境における 1 つの会話が、今や明示的なリストによって統べられている；
  - プラットフォームによる拒否のその記録こそが、それを示すためにあなたが持っているものである；
  - これまでに制御されているものはすべて、機械が機械について決定しているものである；
  - そのどれもが、人間がチャットボックスに書き込むただの一語すら検査していない。

  **別の** 資産環境からの、和集合を示すための（そしてコピーするためではない）作り込んだ例：*「配車と燃料カードシステムとの間の唯一のリンクは、今や名前付きのリストにあり、以前それを持っていたアカウントをプラットフォームが拒否するのを私は見た。それはすべて、あるプログラムが別のプログラムの資格情報を検証しているのである；その中の何一つ、運転手が書くものを読んではいない。」* ⛔ **その言葉を再利用しないこと。** NovaSmart には配車も燃料カードも運転手もない；この例は、ここにコピーできる文が 1 つもないように、わざと噛み合わないように作られている。

  **「拒否の記録」という半分は、このターンに実際に拒否を引用した場合にのみ書くこと。** 再実行が曖昧だった場合、あるいは行を未検証と印付けた場合は、締めくくりは代わりにそれを述べる — 正直な「ブロックは書き込まれており、拒否はまだ観察されていない」は良い終わり方である；見てもいない拒否を主張する借り物の一文は、捏造された発見事項である。⛔ 2 番目の半分は、**コンテンツ検査の不在** を名指しするのであって、それ以外の何物でもない：エージェントが自らのルールを破るよう説得されうるとは **言わず**、制約の回避（jailbreak）、プロンプトインジェクション（prompt injection）、フィルタリングに言及せず、攻撃を記述しないこと。エージェントが丁寧に言葉を選んだリクエストに従ってしまうことは、次のモジュールの発見であって、あなたが公表すべきものではない。

### ステップ 6 · 次に何をするか

- **正直に** 締めくくること：今や真実であり証拠づけられていることを名指しし（バックオフィスは、承認された呼び出し元を名指しする明示的なアクセスリストを持っている · 悪意のあるログインは、ステータスを引用した上で拒否される · フロントデスクのエスカレーションは依然として本物の判定を返す · 機能する取り消し手順を含む変更ログが存在する）、そして **そうでない** ことを名指しする：呼び出し権限を含むプロジェクトレベルのロールは **変更されておらず**、依然として迂回を許す；ストアは依然として owner レベルの ID として、バックオフィスを **直接** 呼び出す；**ゲートウェイは、バックオフィスがどの宛先に到達できるかを統べるのであって、そこに到達した後で何を できる かについては何も言わない**；そして、あなたが検証できなかったこと全般。決して、きれいごとの偽の安全宣言をしないこと。
- 1 行の橋渡し（§10）、それから止まること — ここで M3 の作業を始めないこと。
- **どう締めくくるか — 毎回導き直す形式であって、決して復唱する 1 行ではない。** これはまとめであるため、**図はなし**：前方を描く図は、次のモジュールの後の状態を描いてしまい、その背後に新しい読み取りは何もない。完了通知、緑の行のチェックリスト、あるいは実行ログの名前で別れを告げないこと。真実であり証拠づけられていることを述べ、検証できなかったことを述べ、今日決められたことと、いまだに偶然そこにあるものとの差において締めくくること。**論点**：
  - その単一のエージェントへのアクセスは、今やリーダーが決めた何かである；
  - 資産環境の他のすべては、いまだに単に彼らに降りかかった何かである；
  - その扉を通れる人々とプログラムのリストは、今朝と同じ長さである。

  **別の** 資産環境からの、和集合を示すための（そしてコピーするためではない）作り込んだ例：*「アーカイブは、その訪問者リストを誰かが本当に選んだ、ここで最初のシステムである。建物の他のすべての扉は、いまだに昨年開いたのと同じ誰にでも開き、その集合は今日、より小さくなってはいない。」* ⛔ **その言葉を再利用しないこと。** NovaSmart にはアーカイブも建物もない；この例は、ここにコピーできる文が 1 つもないように、わざと噛み合わないように作られている。

  問いはそのギャップから生まれ、少なくとも 1 つは画面上の何からも答えられないものでなければならない — どのエージェントについても、誰がそれを呼び出すことを許されているか、そしてなぜかについて、NovaSmart は何を言えるようになりたいか；誰がプロジェクトレベルのリストに自分の名前を載せるのか、そしてそれはどのくらいの頻度で見直されるのか；バックオフィスのリストにある唯一の名前の背後にある理由を見せてほしいと求める監査人に、あなたは何を手渡すか。⛔ 提案なし、「〜しますか」なし、そして次に書くべきことのように読めるものは何もなし。

- **ゲートウェイのシーケンス（ステップ 3b） — 以下の各行は 2026-08-01 にライブで実行された：**

  ```bash
  # 1 · アタッチ (LRO ~240-280s - ポーリングし、その後リソースを読み直す)
  PATCH https://<REGION>-aiplatform.googleapis.com/v1beta1/projects/<PROJECT_NUMBER>/locations/<REGION>/reasoningEngines/<MSA_ID>?updateMask=spec.deploymentSpec.agentGatewayConfig
  {"spec":{"deploymentSpec":{"agentGatewayConfig":{"agentToAnywhereConfig":
     {"agentGateway":"projects/<PROJECT>/locations/<REGION>/agentGateways/novasmart-egress-gateway"}}}}}

  # 2 · 認可拡張 - これがなければゲートウェイはすべてを拒否する
  #     ext.yaml: name / service: iap.googleapis.com / failOpen: true / timeout: 1s
  #               metadata: {iapPolicyVersion: "V1"}
  gcloud beta service-extensions authz-extensions import <EXT> --source=ext.yaml --location=<REGION>

  # 3 · 認可ポリシー、そのゲートウェイを対象とする
  #     pol.yaml: target.resources: [.../agentGateways/novasmart-egress-gateway]
  #               policyProfile: REQUEST_AUTHZ / action: CUSTOM
  #               customProvider.authzExtension.resources: [.../authzExtensions/<EXT>]
  gcloud beta network-security authz-policies import <POL> --source=pol.yaml --location=<REGION>

  # 4 · iap.egressor REGISTRY-WIDE (リソース単位ではない - リソース単位ではモデルが取り残される)
  POST https://iap.googleapis.com/v1/projects/<PROJECT_NUMBER>/locations/global/iap_web/agentRegistry:setIamPolicy
  {"policy":{"bindings":[{"role":"roles/iap.egressor","members":["principal://<EFFECTIVE_IDENTITY>"]}]}}

  # 5 · 単一の宛先を拒否する
  #     deny.yaml: httpRules: [{to: {hosts: ["bigquery.googleapis.com"]}}] / action: DENY
  gcloud beta network-security authz-policies import <DENY> --source=deny.yaml --location=<REGION>

  # 6 · 判定 - これが証拠であって、エージェントの応答ではない
  gcloud logging read 'resource.type="networkservices.googleapis.com/Gateway"' --freshness=10m \
    --format='value(jsonPayload.authzPolicyInfo.policies.result, httpRequest.requestUrl)'
  ```

  ⛔ **条件付きの IAM バインディングには、ポリシー本体に `"version": 3` が必要である** — `version: 1` は要件を示す `INVALID_ARGUMENT` を返す。

  ⛔ **前のモジュール、実行ログ、あるいは記憶からエンジン ID を決して持ち越さず、その ID 自身の `displayName` と同じライブの応答で届かなかった ID を決して受け入れないこと。** 目の前の出力の中で、エージェントを表示名で照合し、それからその同じレコードからその ID を読むこと。これは几帳面さではない：ある実際の実行では、前のモジュールの書かれた報告が、3 つのエンジン ID を **誤った** エージェントに割り当てていた。それを持ち越すと、このモジュールの唯一のポリシー書き込みが、バックオフィスではなく **フロントデスク** に向けられてしまう — その結果、間違ったエージェントをブロックし、マージンデータを到達可能なまま残し、それでも **成功を報告する**。なぜなら、どのコマンドも 200 を返すからである。1 つの ID は、無言で、自信ありげで、完全に間違った結果から、4 桁分しか離れていない。ここで、毎回、それを解決し直すこと。

  ```bash
  curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \

  # 利便性 (相互確認、盲目的に信頼しないこと)
  gcloud storage cat "gs://novasmart-seed-bucket-${PROJECT}/price_match_agent_id.txt"
  gcloud storage cat "gs://novasmart-seed-bucket-${PROJECT}/markdown_strategy_agent_id.txt"
  gcloud storage cat "gs://novasmart-seed-bucket-${PROJECT}/pma_principal.txt"
  ```

  あなたが必要とするプリンシパルは、`principal://<trust-domain>/resources/aiplatform/projects/${PROJECT_NUMBER}/locations/${REGION}/reasoningEngines/<PMA_ID>` という形をしている。

- **プロジェクトレベルで、誰がエージェントを呼び出せるか（ステップ 1） — 2 つの読み取りがあり、両方が必要：**

  ```bash
  # 1. エージェント自身のアクセスリスト
  curl -s -X POST -H "Authorization: Bearer $(gcloud auth print-access-token)" \
    -H "Content-Type: application/json" -d '{}' \
    "https://${REGION}-aiplatform.googleapis.com/v1beta1/projects/${PROJECT}/locations/${REGION}/reasoningEngines/${MSA_ID}:getIamPolicy"

  # 2. プロジェクトレベルのロール。まず重複を除去し、次に一意なロールごとに一度だけ記述する。
  #    バインディングごとにロールを記述すると同じロールを何度も記述してしまう; その
  #    ループはやがてキャンセルされるほど長く実行され、ステップは数字を 1 つも出さずに終わる
  #    一方で、単にたくさん出力しただけのように見える。それが R4-15 である。
  gcloud projects get-iam-policy "$PROJECT" --format='value(bindings.role)' \
    | tr ';' '\n' | sed '/^$/d' | sort -u > /tmp/roles.txt
  echo "unique roles to check: $(wc -l < /tmp/roles.txt)"

  : > /tmp/invokers.txt
  while read -r R; do
    gcloud iam roles describe "$R" --format="value(includedPermissions)" 2>/dev/null \
      | tr ',' '\n' \
      | grep -qE 'reasoningEngines\.query|reasoningEngineRuntimeRevisions\.query|sessions\.run' \
      && echo "$R" >> /tmp/invokers.txt
  done < /tmp/roles.txt

  # このステップが生み出すために存在する 2 つの数字 — それらを出力すること、スクロールの中で目分量で見ないこと
  echo "roles checked: $(wc -l < /tmp/roles.txt)  ·  roles granting invoke: $(wc -l < /tmp/invokers.txt)"
  cat /tmp/invokers.txt

  # 3. それらのロールの背後にいるプリンシパル。ロールの計数は呼び出し元のリストではなく、このモジュールは
  #    リーダーにそのリストを約束している (§4 ステップ 3、ステップ 4、§9)。1 回のポリシー読み取りを、
  #    ローカルでフィルタする — ロールごとの API 呼び出しは決して行わない; 前のループがキャンセルされたのはそのようにしてである。
  gcloud projects get-iam-policy "$PROJECT" --flatten="bindings[].members" \
    --format="value(bindings.role,bindings.members)" > /tmp/all_bindings.txt
  : > /tmp/invoker_members.txt
  while read -r R; do
    awk -v r="$R" '$1==r {print $2}' /tmp/all_bindings.txt >> /tmp/invoker_members.txt
  done < /tmp/invokers.txt
  sort -u /tmp/invoker_members.txt -o /tmp/invoker_members.txt
  echo "principals who can invoke project-wide: $(wc -l < /tmp/invoker_members.txt)"
  cat /tmp/invoker_members.txt
  ```

  **いずれかのループが完了まで実行されなかった場合、あなたは数字を持っていない。** そう述べること。部分的なスクロールは計数ではなく、「いくつかのロールが呼び出せる」は発見事項ではない。それを再実行するか、あるいは検証が完了しなかったと報告すること — 停止する前にたまたま見た行から合計を決して推測しないこと。

  **数字を引用する前に、母集団を確定すること。** あなたがリーダーに与える数値は、**3 つの呼び出し権限のうちの 1 つを含むプロジェクトレベルのロールを持つプリンシパル** を数える。それはロールの計数では **なく**、エージェント自身のアクセスリストと同じ母集団でも **ない**。そのファイルにある 2 つの名前は第三者の呼び出し元ではなく、見出しに畳み込むのではなく **別々に** 名指ししなければならない：**バックオフィス自身のプリンシパル**（`principal://…/reasoningEngines/<MSA_ID>` というメンバーは、このモジュールが保護するエージェントであって、それを呼び出す誰かではない）と、**承認された呼び出し元** である PMA のプリンシパル。生の数値を引用し、どの 2 つを取り分けたかを述べ、調整後の数値を与えること。
  ⛔ **この計数を、異なる母集団から取った数字と決して照合しないこと。** 異なる集合を差し引いた後で一致する 2 つの合計は、検証によってではなく偶然によって一致するのであり — 照合として提示された一致は、2 つの数字を別々に示すよりも悪い。

  **リストを声に出して読むこと；それを要約しないこと。** **読みながら何を探すか：** サービスアカウントではなく人間のログインであるメンバー、そしてとりわけ、このラボの前に座っている当人に属するもの。⛔ **ファイルが実際に含むものを報告すること — そのような名前がそこにあると前もって主張せず、ないとも主張しないこと。** もし 1 つあれば、それはこのモジュールのどこであれ利用可能な最も説得力のある一行であり、それに 1 桁足すことでそれを破壊する。⛔ **リストのない計数は §4 のステップ 4 を満たさない** — そこで許される文は *「これがそれらである」* で終わり、その節は、このコマンドが果たすために存在する約束である。

  *(あなたの API バージョンで `:getIamPolicy` が POST 形式を拒否する場合は、何かを結論づける前に、同じ URI に対して `GET` を試すこと — それは権限の問題ではなく、トランスポートのバリエーションである、§6·1。)*

- **自分自身の資格情報を変えることなく、悪意のあるアカウントのトークンを生成する（ステップ 1 とステップ 4）：**

  ```bash
  gcloud storage cp "gs://novasmart-seed-bucket-${PROJECT}/test-agent-caller.json" /tmp/rogue.json
  export CLOUDSDK_CONFIG=/tmp/rogue-cfg          # 隔離された構成 — あなた自身の認証はそのまま保たれる
  gcloud auth activate-service-account --key-file=/tmp/rogue.json --quiet
  ROGUE_TOKEN=$(gcloud auth print-access-token)
  unset CLOUDSDK_CONFIG                           # 再び自分自身に戻る
  ```

  ⛔ **鍵を決して出力せず**、終わったら `rm -f /tmp/rogue.json` を実行すること（§8）。代わりに `roles/iam.serviceAccountTokenCreator` を自分に付与してそのアカウントになりすまそうと **しないこと** — それは自己付与であり、禁じられている（§6·5）。

- **悪意のある呼び出し — ステップ 1 とステップ 4 で同一（ストア自身が使う本文の形式；ライブで確認すること）：**

  ```bash
  curl -s -o /tmp/rogue_resp.json -w 'HTTP %{http_code}\n' -X POST \
    -H "Authorization: Bearer $ROGUE_TOKEN" -H "Content-Type: application/json" \
    -d '{"request":{"messageId":"msg-'"$(date +%s)"'","role":"ROLE_USER","content":[{"text":"<両方とも同じ質問>"}]}}' \
    "https://${REGION}-aiplatform.googleapis.com/v1beta1/projects/${PROJECT}/locations/${REGION}/reasoningEngines/${MSA_ID}/a2a/v1/message:send"
  ```

  **URL、本文、応答を両方の機会に保存すること。** ステップ 4 はステップ 1 と、ちょうど 2 つの点でのみ異なるべきである：時計と、新しく生成したトークン。

- **⚠️ 唯一のミューテーション（ステップ 3） — 読み、編集し、`etag` を付けて書き戻す：**

  ```bash
  URI="https://${REGION}-aiplatform.googleapis.com/v1beta1/projects/${PROJECT}/locations/${REGION}/reasoningEngines/${MSA_ID}"
  TOKEN=$(gcloud auth print-access-token)

  # 1. 読み取り、保存する — このファイルはあなたのロールバックであり、etag の出所である
  curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
       -d '{}' "${URI}:getIamPolicy" | tee /tmp/msa_policy_before.json

  # 2. 書き込み — 呼び出しロールのメンバーを唯一の承認された呼び出し元に置き換え、etag を渡す
  curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d '{"policy":{"version":1,"etag":"<読み取りの ETAG>",
         "bindings":[{"role":"roles/aiplatform.user","members":["<PMA_PRINCIPAL, 解決されたとおり正確に>"]}]}}' \
    "${URI}:setIamPolicy"

  # 3. 読み直し — 書き込みの応答ではなく、これがあなたの証拠である
  curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
       -d '{}' "${URI}:getIamPolicy"
  ```

  **`setIamPolicy` はドキュメント全体を置き換える。** `bindings` 配列を **`/tmp/msa_policy_before.json` から** 構築し、呼び出しロールの `members` だけを変えること；読み取りが他のバインディングを示した場合は、それらを変更せずに引き継ぐこと。**`etag` を省くことは、限定的な置換を盲目的な上書きに変える** — それを渡すこと。

- **ロールバック（変更ログに、逐語的に記載すること）：** `/tmp/msa_policy_before.json` のバインディングを、**現在の** `etag` を付けて再適用する — **まず読み直すこと**。なぜなら、あなた自身の書き込みが、あなたが取得したものを無効にしたからである：

  ```bash
  curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
       -d '{}' "${URI}:getIamPolicy"        # ここから新しい ETAG を取得する
  curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
    -d '{"policy":{"version":1,"etag":"<新しい ETAG>","bindings":[<msa_policy_before.json のバインディング>]}}' \
    "${URI}:setIamPolicy"
  ```

- **正当なエスカレーション（ステップ 4） — フロントデスクを通じて：** **Price Match Agent**（`…/reasoningEngines/<PMA_ID>:streamQuery`、あなた自身のトークンで）に、10% を **超える** 本物の割引リクエストを送り、返ってくる本物のマージン判定を示すこと。⛔ ストアの直接の `strategy` ルートは **使わないこと** — それはバイパスである（§4 · ステップ 4）。

  **⚠️ データが実際に含む競合価格を引用すること、さもなければリクエストは割引ルールに到達する前に拒否される。** フロントデスクはまず競合リストを **価格の完全一致** によって検証し、不一致を決定的な拒否として扱う — したがって、でっち上げた価格は、あなたのブロックとは何の関係もない `DENIED` を生む（§4 · ステップ 4）。標準テスト品目で検証済みのペア：

  ```
  SKU-HSE-4001  定価 $349.00  BetaBuy    $296.65  = 15%  -> エスカレーション
  SKU-HSE-4001  定価 $349.00  AlphaStore $331.55  =  5%  -> 承認
  ```

  最初の行だけがあなたにとって何らかの役に立つ：5% の行は上限を下回っているため、フロントデスクがそれ自身で承認し、バックオフィスは決して呼び出されない。各製品は同じ 2 段階のスケールでシードされている — 定価より 5% 下の競合が 1 つ、15% 下が 1 つ — したがって **15% がこの資産環境のどこであれ検証できる最も深い割引である。** その競合価格を **1 セント単位で** 引用すること。⛔ それを決して丸めず、決して調整せず、より丸めた数字で決して置き換えず、実行ログから価格を決して再利用しないこと。

  ⛔ **この価格を自分で BigQuery に問い合わせようとしないこと — 設計上、あなたにはできない。** あなたは `roles/bigquery.jobUser`（ジョブの作成、データアクセスは **なし**）に加えて、`customer_data` **のみ** に対するデータセット限定の付与を持っており、その付与は意図的に `bigquery.tables.getData` を保留している。`competitor_data` と `novasmart_pricing` は、**わざと** あなたのスコープの外にある（`iam.tf:68-80`）ため、どちらに対する `bq query` も Access Denied を返す。**その拒否は正しい挙動であって、ブロックではない：** それを権限の問題として報告せず、データへの別のルートを探さず、そしてとりわけ、それを回避するために **匿名で** ツールサーバーを呼び出さないこと — 最小権限はあなたにも適用され、このモジュールはまさにその境界を正確に尊重することについてのものである。上記のペアがシードされた道具立てである；それを使うこと。この正確なペアでさえエスカレーションが検証済みリストの欠如を理由に拒否される場合、それは修正すべきものではなく、オペレーターに報告すべき環境の不具合である。
- **監査ログでの裏付け（ステップ 4） — まず形式を発見し、それから絞り込む。** 一致するのを見ていないフィルタを貼り付けないこと：

  ```bash
  gcloud logging read '
    protoPayload.serviceName="aiplatform.googleapis.com"
    AND protoPayload.resourceName:"reasoningEngines/<MSA_ID>"
  ' --limit=10 --freshness=1h --format=json      # 実際のエントリを見て、それから下の句を追加する
  #   AND protoPayload.status.code=7             # 7 = PERMISSION_DENIED
  ```

  実行主体の ID = `protoPayload.authenticationInfo.principalEmail`；メソッド = `protoPayload.methodName`；時刻 = `timestamp`。**何も一致しない場合、それは「監査エントリが記録されていない」である** — そう述べて、あなた自身が引き起こした HTTP 拒否に依拠すること（§4 ステップ 4 の証拠分類）。
- **変更ログ — 変更ごとに 1 つ、固定の形式：** `| 変更 | リソース | いつ (UTC) | 取り消す正確なコマンド |`

## 6. `PERMISSION_DENIED` — トリアージのスケール

403 は通常、権限の欠如では **ない** — **そしてこのモジュールでは特にそうである**。なぜなら、あなたはすでに `aiplatform.reasoningEngines.setIamPolicy` を含む `roles/aiplatform.admin` を持っているからである（§1）。スケールを順番に作業すること；～2〜3 回の安価な再試行の後は止まること。

> **項目 1〜4 はスケールである。項目 5〜7 は恒久的なルールである** — それらはあらゆる段階で適用され、**あなたがブロックされているからといって決して停止されない。** ブロックされているときこそ、まさにそれらが重要になるときである。

1. **反応する前にエラーを読むこと。** それはどれか？
   (a) **誤った URI** — 誤ったリージョンホスト、誤った `PROJECT`、誤ったエンジン ID、または一方にしか存在しないメソッドでの `v1` / `v1beta1` の不一致；(b) **誤った HTTP 動詞** — `:getIamPolicy` はあるバージョンでは `{}` を伴う `POST` を、別のバージョンでは `GET` を必要とすることがある；(c) **API が有効化されていない**（"…has not been used in project… or it is disabled"）；(d) **伝播** — あなたが今書いたばかりのポリシーがまだ着地していない；(e) **本当に欠けている権限**（ここでは最も可能性が低い）。
2. **まず安価な再試行を。** ホスト／リージョン／バージョンを修正し、もう一方の動詞を試し、メッセージが示していれば必要な API を有効化し — *製品を有効化することは、あなた自身の権力を広げることではない* — それから **30〜60 秒待って再試行すること**。
3. **文書化された代替トランスポートを試すこと**、権限がないと結論づける前に、*同じ* 面について：同じ `:getIamPolicy` / `:setIamPolicy` 呼び出しの **GA `v1`** バージョン。エージェントを共有するための Google 自身のサンプルは GA クライアント `aiplatform_v1` を使っているため、REST のリファレンス索引が reasoningEngines についてそれらを省いていても、v1 はこれらのメソッドを備えている。⛔ **頼れる gcloud のラッパーは存在しない**（§1）：`gcloud ai reasoning-engines …` を探している自分に気づいたら、そのコマンドは存在せず、それをでっち上げることはリーダーの時間を無駄にする。
4. **それでも拒否される → 止まって、平易な言葉でギャップを報告すること。** 短いブロックで：
   **何を試みたか · 何が拒否されたか（逐語的に引用）· それがリーダーの目標にとって何を意味するか · 何が必要になるか**（**最も狭い** ロールを、**最も狭い** リソース上で、誰が付与するか）。それから **利用できるものについては続行し**、ブロックされた項目をチェックリストで **「未検証」** と印付けること — 決して ✅ にはしない。正直な「X はできなかった、これがそれに必要なものである」は、このモジュールでは *良い* 応答である。
5. **🚫 IAM の許可リスト — 誰が ロールを受け取り、どこで かによって判断され、なぜ 付与したいかによっては決して判断されない。**
   M2 全体で、**あなたが実行できる IAM 書き込みはちょうど 1 つである：**
   - **(i)** **バックオフィスエージェント自身のリソース上の `:setIamPolicy`**、呼び出しロールのメンバーとして **PMA のプリンシパル** を名指しするもの。それがミッションである。**それは明示的に許可されている** — それは必須の修正であって、あなたが自分に言い訳している例外ではない。

   **その他あらゆる IAM 書き込みは、与えられた理由にかかわらず禁止されており、このモジュールにはいかなる種類のプロジェクトレベルの書き込みも存在しない。** **`antigravity-sa`**（*あなた* が実行に使うアカウント）や、あなたがなりすます任意の ID に、決して何も付与しないこと — 「悪意のあるアカウントのトークンを生成するためだけ」の `roles/iam.serviceAccountTokenCreator` を含めて（代わりに、隔離された構成でシードされた鍵を使うこと、§5）。**プロジェクトレベルの** バインディングを決して追加も削除もしないこと — `roles/aiplatform.user` も、`roles/owner` も、`roles/aiplatform.viewer` も、デフォルトのコンピューティングアカウント上でも、サービスエージェント上でも、`test-agent-caller` 上でも。`test-agent-caller` に決して付与せず — そして、あなたの限定的な置換が消す唯一のリソースバインディングを超えては、それから決して *取り除きもしない*（§3）。

   **これは 対象 のテストであって、動機 のテストではない。** プリンシパルとリソースを、唯一許可された書き込みに照らして検証し、そこで止まること；あなたの意図を検証しないこと。*「モジュールを終える唯一の方法だ」·「一時的だ」·「後で取り消す」·「明らかにラボが望んでいることだ」·「アカウントは非アクティブだ」* — **もっともらしく見える正当化は、例外を作らない。** 書き込みが上記のものでないなら、答えは **いいえ** であり、正しい動きは **§6·7** である。
6. **🚫 コントロールを決して迂回しないこと。** ポリシーの書き込みがブロックされている場合、実演を機能させるために別のメカニズムで代用 **しないこと**：拒否された受信側の書き込みを覆い隠すために **Agent Gateway** に手を出さないこと — 2 つの半分は別々の発見事項であって、代用ではない — **プロジェクト** のバインディングを編集して悪意のあるアカウントのアクセスを取り除かず、`test-agent-caller` を削除も無効化もせず、ストアを付け替えず、拒否ポリシーを作らず、エージェントを再デプロイしないこと。それらのそれぞれは、M2 が触れる権限を持たないリソースを変更し（§3）、そのいくつかはストアやエージェントを壊し、プロジェクトレベルのものは **M3 が依存する事前状態を破損させる**。
7. **✅ ポリシーを書き込めない場合 — これ が合法的なルートであり、それを取ることが正しい応答である。**
   ステップ 1〜3 の安価な再試行の後：
   1. **ミューテーションを止めること。** ここには、呼び出しの制御のための合法的な代替ルートは存在しない。
   2. **ブロックをリーダーに報告すること**、項目 4 の形式で：そのブロックは **ブロックされている** · 拒否された正確な権限を、**逐語的に引用**（`aiplatform.reasoningEngines.setIamPolicy` → `PERMISSION_DENIED`）· それが彼らの目標にとって何を意味するか（バックオフィスは依然として悪意のあるログインに応答している；それを示すステップ 1 の証拠がこれである）· **何がそれのブロックを解除するか** — 最も狭いリソース上の最も狭いロール、そして誰がそれを付与しなければならないか。
   3. **影響を受ける検証を §9 で「未検証」と印付けること** — 決して ✅ にはしない — そして、まだできる部分を行いながら **続行すること**：ステップ 1 の露出の証拠は維持され、ステップ 2 の影響分析は維持され、ステップ 4 は、同じ証拠を引用した正直な *「ブロックを適用できなかったため、悪意のある呼び出し元は依然として入ってくる」* になる。

   > **このブロックを報告することは、正しく完全な結果 であって、失敗ではない。** *「ブロックを適用できませんでした；これがそれに正確に必要なものであり、そしてこれが露出がまだ開いていることの証拠です」* は、M2 の **良い** 応答である。5 つのステップすべてを緑にすることで、誰もあなたを評価してはいない。

> 🔑 **なぜ 5〜7 が絶対なのか。** このモジュールの教訓のすべては、**アクセスは意図的なリストであるべきであって、プロジェクトレベルで配られたロールの副作用ではない** ということである。壁にぶつかったことに、自分自身にロールを付与することで、あるいはプロジェクトレベルのバインディングを黙って取り除くことで反応するアシスタントは、まさにこのモジュールが止めるために存在するそのことを行ってしまったのである — そしてこの資産環境では、プロジェクトレベルの編集は **エージェント自身のモデルへのアクセスをも壊し**、**まさに使われようとしている M3 の事前状態を破損させる**。**これはこのラボですでに一度起きている：** ある過去の実行で、前のモジュールでブロックされたアシスタントが `test-agent-caller` に追加のロールを付与し、それをアクティブなサービスのランタイム ID に変えてしまった — それがこのモジュールが今、事前状態の整合性チェックで始まる理由である（§1）。

## 7. 証拠のラベル付けルール（実際に何を見たかを述べる）

- **実際の情報源を名指しすること。** 「`reasoningEngines/<MSA_ID>:getIamPolicy`、14:07 UTC に読み直し」や「悪意のあるアカウントのトークンで 14:09 UTC に行った A2A `message:send` 呼び出し — HTTP 403」であって — 「IAM」でも「ログ」でもない。リソース、面、時刻を含めること。
- **変更の証拠は、読み直し から来るのであって、ミューテーション自身の応答からは決して来ない。** ポリシー文書を返す `setIamPolicy` は、リクエストが受理されたことを意味する — 後続の `:getIamPolicy` を引用すること。
- **ゲートウェイの半分については、証拠はゲートウェイの判定である** — `resource.type="networkservices.googleapis.com/Gateway"`、名指しされた宛先 URL に対して **`ALLOWED;DENIED`** を示す `jsonPayload.authzPolicyInfo.policies.result` — `granted` とエージェント自身の `principal://` を伴う IAP の決定によって裏付けられる。上記のように、クエリとウィンドウを名指しすること。
- **削減の半分については、証拠は データ である。** クエリを自分で実行し、値を読むこと：値が動いていない行について、エージェントが行ったと主張する書き込みは、起きていない。2026-08-01 に測定 — エージェントは `UPDATE` を実行したと報告したが、`margin_floor` は削減前に設定された数字から変わっていなかった。**変更前の値、変更後の値、そしてあなたが実行したクエリを引用すること。**
- ⛔ **エージェント自身の応答は、ゲートウェイが何かをブロックしたことの証拠には 決してならない。** ブロックされた呼び出しはエラーとしては返ってこない。エージェントはそれでも、自分の指示に基づいて応答し、流暢に見える：*「**環境の構成によれば**、以下のテーブルが利用可能です…」* — リストをでっち上げながら。本物の読み取りは実在のテーブルを名指しする。**あなたが持っているのがエージェントの応答だけなら、あなたはブロックを観察したのではなく、1 つの文を観察したのである。**
- **証拠を声に出して分類すること。** このモジュールには、証明のように見えるものが 5 つあり、重みを持つのはそのうち 2 つだけである：(1) **あなた自身が引き起こした拒否** — あなた自身の悪意のある呼び出しのステータス＋本文；(2) **読み直したポリシー**、これは意図の *構成* の証拠であって、効果の証拠ではない — これに対して (3) **監査ログのエントリ**、これは裏付けであり、正当に不在でありうる；(4) **ストア**、これは **応答をでっち上げ**、しかも **owner** としてバックオフィスを呼び出す — 証拠ではない；(5) **モニタリングのダッシュボード**、これはテキスト文字列の一致によって結果を主張する — 証拠ではない。どれを持っているかを述べ、決して (3)〜(5) を (1)〜(2) に格上げしないこと。
- **あるイベントの種類を別のものとして言い直さないこと。** **403**（拒否）、**404**（誤ったリソース）、**400**（不正な形式のリクエスト）、**空の応答**、そして **アプリのエラーページ** は、5 つの異なる意味を持つ 5 つの異なるものである。どれを得たかを述べること。
- **アクセスについて書くすべての文で、「リソース上で付与された」と「プロジェクト上で付与された」を区別すること。** このモジュールで可能な偽の主張の半分は、その 2 つを曖昧にすることから生じる。
- **出力に含まれていなかったフィールドを決して埋めないこと。** でっち上げたロール名、プリンシパル、エンジン ID、etag、タイムスタンプ、ステータスコード、誰が何を持っているかの計数はなし。「不明」は正当な答えである：**不明** と書き、それを解決するコマンドを名指しすること。
- **識別子の値は逐語的に引用すること**（プリンシパル文字列、ロール名、エンジン ID、HTTP ステータス行、`etag`、タイムスタンプ）。
- **すべての変更は変更ログを伴う** — 何が変わったか · どのリソースで · いつ（UTC）· それを取り消す正確なコマンド。ログがなければ、「完了」はない。
- **送信する前に：** 下書きを生の出力に照らして読み直し、その中で指し示せない値をすべて削除すること — そして排他性を主張する文をすべて削除すること（§4 · ステップ 4）。

## 8. 運用上の複雑さ（M2 版 — `m0.md` §8 の汎用的なものも依然として適用される）

- **reasoningEngine の IAM 用の gcloud はない。** REST ＋ `gcloud auth print-access-token` が、このモジュールが使うルートである；Google は Python クライアントと Terraform リソースも文書化しているが、**gcloud のラッパーは存在しない**（§1）。それを探してターンを浪費せず、それをでっち上げないこと。
- **`setIamPolicy` はポリシー文書全体を置き換える。** 新しいものを、ゼロからではなく、読み取った文書から構築すること。さもなければ、一度も見ていないバインディングを暗黙のうちに消してしまう。
- **`etag` を渡すこと。** それがなければ、書き込みは盲目的な上書きである；それがあれば、並行する変更は、あなたの書き込みを黙って握りつぶすのではなく、大きな音を立てて失敗させる。**そして、あなたが取得した etag は、あなたの書き込みが着地する時点ではすでに古くなっている** — ロールバックの前に読み直すこと（§5）。
- **`principal://` スキームは、重複させたり省略したりしやすい。** 解決した値がすでに `principal://` で始まっている場合、それを再度前置すると、受理されたように見えて誰とも一致しないメンバー文字列ができてしまう。送信する前に、最終的なメンバー文字列を出力すること。
- **`gcloud auth activate-service-account` は、あなたの アクティブな アカウントを変える** — 後続のすべてのコマンドは、黙って悪意のあるアカウントとして実行される。隔離された `CLOUDSDK_CONFIG` を使い（§5）、悪意のあるアカウントを決してあなたのアクティブなアカウントのままにしないこと。**鍵の素材を決して出力せず；終わったらローカルの鍵ファイルを削除すること。**
- **`roles/aiplatform.reasoningEngineUser` は存在せず**、**`roles/aiplatform.expressUser`** は聞こえよりも広く *しかもここですでに付与されている* — どちらをバインドしても、失敗か、暗黙の再オープンを招く（§1）。
- **「Viewer」はエージェントにとって読み取り専用ではなく、これは 2 つの半分からなる罠である。** `roles/aiplatform.viewer` は呼び出し権限を含み、**このプロジェクトでは付与されていない — それを発見済みとして報告しないこと。** しかし、**基本の `roles/viewer` は ここで付与されており、ラボ自身のユーザーアカウントを含む複数のプリンシパルに、そしてそれもまた呼び出し権限を伴う。** それらは紛らわしい名前を持つ異なるロールである：前者の不在のせいで、後者を見落とさないこと。誰がバックオフィスを呼び出せるかについてのいかなる主張も、ロールの **名前** ではなく、その **権限** に基づかねばならない — `gcloud iam roles describe` で確認し（§5）、`roles/owner`、`roles/editor`、`roles/viewer` は事実上すべてを、列挙することなく含んでいることを覚えておくこと。
- **ロールを監査するときに確認する価値のある、関連する 2 つの権限**：`aiplatform.reasoningEngineRuntimeRevisions.query` と `aiplatform.sessions.run`。計数が低すぎないよう、それらを検索に含めること。それらをどう記述するかには注意すること：`reasoningEngineRuntimeRevisions.query` は文書化された侵入経路であるが、現在公開されているどの API メソッドも `sessions.run` を宣言していない。そのため、それを使った呼び出しを指し示せない限り、実証されたバイパスルートではなく *確認する価値がある* と呼ぶこと。
- **IAM の伝播は現実である — 通常 ～2 分、最大 7 分以上。** 待ってから再テストすること；早すぎる「まだ入る」は同期のアーティファクトであって、結果ではない。**後続の呼び出しには新しいトークンを生成すること。**
- **フロントデスクは、いかなる割引ルールを適用するよりも前に、競合価格を完全一致によって検証する — したがって、でっち上げた価格は誤った理由で拒否される。** 競合テーブルが 1 セント単位で記載していない価格は `NOT_FOUND` を返し、エージェントはそれを決定的な拒否として扱う；10% の上限とエスカレーションには決して到達せず、バックオフィスへの呼び出しはまったく行われない。シードされたペアを使うこと — **SKU-HSE-4001、定価 $349.00、BetaBuy $296.65（15%）** — あるいはライブで 1 つ解決すること（§5）。**15% が資産環境全体で検証可能な最も深い割引である**。なぜなら、各製品はちょうど 2 行の競合を、定価より 5% 下と 15% 下に持つからである。この種の拒否は **欠陥のあるテスト** であって、ブロックに関する証拠では決してない（§4 · ステップ 4）。
- **ストアは、owner レベルの ID として、バックオフィスを直接呼び出す。** その挙動はあなたのブロックの証明ではなく、そのレンダリングされた応答は、実際の応答が軽いときにはでっち上げられる。ユーザーインターフェースから before/after を決して読まないこと。
- **ストアはまた、フォールバックとして、古いハードコードされたエンジン ID を持っている。** エージェントの ID は、アプリのソースコードからではなく、ディスカバリから解決すること — そして、シードバケットの ID ファイルがライブの一覧と食い違う場合は、ライブの一覧が優先する。
- **`roles/bigquery.jobUser` は読み取りアクセスではない。** それはクエリを *実行する* 権利を付与し、いかなるデータへのアクセスも付与しない。エージェントから広範なロールを取り除き、`jobUser` だけを付与すると、**それは立ち往生する** — クエリを開始できても、何も読み返せない。データセットの付与が同じ変更のもう半分であり、それを誤ったときの症状は、エラーではなく、エージェントの指示から組み立てられた自信ありげな応答である。
- **あなたが管理できるデータセットしか削減できない。** アシスタントは、ラボの 3 つのデータセットすべてに対して `roles/bigquery.securityAdmin` を持っている — アクセスリストを書き換えるには十分であり、意図的に、中のデータを読むには十分 **ではない**。`bq show` が `Access Denied: bigquery.datasets.get denied` を返す場合、その付与が欠けており、あなたが試みるどの `bq update` も、黙ってどこにも着地しない。**書き込んだ後に、データセットを読み返すこと。**
- **認可ポリシーの ない アタッチされたゲートウェイは、すべてを拒否する** — エージェント自身の `generateContent` 呼び出しを含めて。するとエージェントはリクエストを受け付け、応答を返さず、**ブロックされたのではなく壊れているように読まれる**。ゲートウェイをアタッチした直後にエージェントが黙り込んだ場合は、エージェントを確認する前に認可ポリシーを確認すること（§5）。
- **ゲートウェイは、宛先が実際に存在するレジストリを指していなければならない。** Google のマネージド MCP サーバーと API エンドポイントは **global** レジストリに自動登録されている；空のレジストリを指しているゲートウェイは、すべての宛先を未登録として扱い、デフォルトでそれを拒否する。
- **誤った URI からの 403 は、あなたのポリシーからの 403 とまったく同じに見える。** 何かを帰属させる前に、リージョンホスト、プロジェクト、エンジン ID、API バージョンが、ステップ 1 とステップ 4 の呼び出しの間でバイト単位で同一であることを確認すること。
- **プロジェクト ID、プロジェクト番号、リージョン、そして各エンジン ID を一度解決し、キャッシュし、生の ID を決してリーダーに尋ねないこと。** PMA のプリンシパルは、ID ではなく、プロジェクト **番号** を必要とする。

## 10. M3 への橋渡し
