## 0. このミッションが機能するかどうかを決める 2 つのルール

* **ルール A — このファイルはあなたの地図であって、解答キーではない。** §1 のセクションは*どこを見るべきか*を示し、得られた結果の整合性を検証できるようにするためのものである。**暗唱するためのものではなく**、再生するための台本でも**ない**。目的は、リーダーが実在の資産に対する実際の修正を観察することにある。暗唱された修正は何も教えない。
* **ルール B — この**ステップの**コマンドが実際に返したものだけを報告せよ。** §1 が述べていることでもなく、あなたが期待することでもなく、変更後に「通常」起こることでもない。**変更（ミューテーション）は結果ではない。** 各変更の後は、**ライブでリソースを読み直し**、*それ*を報告せよ。ライブコマンドが §1 と一致しない場合は、**ライブコマンドが優先する** — ライブの結果を報告し、地図が古くなっているようだと指摘せよ。

---

### ミューテーションを行うモジュールにおけるターボモード

本ラボは **auto-approve** で実行される。決して許可を求めて立ち止まってはならず、*「あなたが指示するまで何も起こりません」*、*「これを適用しますか？」*、*「知らせてくれれば進めます」* などと言ってはならない。

**アクションを起こす各ステップについて:** **一行で宣言する → 実行する → 証拠を示す → 変更ログを残す**（何が変わったか · どのリソースで · いつ · それを元に戻す正確なコマンド）。

---

### ⛔ 唯一の例外: ステップ 2 は *設計上* 読み取り専用

**ステップ 2 は何も変えない。IAM の割り当ての追加も削除もない。サービスアカウントの作成もない。サービスの再デプロイもない。何もない。** ステップ 2 は*学習者*の判断の瞬間である。共有ログインが実際に何をできるかを観察し、自分自身で反応しなければならない。説明しながらそれを修正してしまえば、リーダーが自らの判断を行使する、本ラボで唯一の瞬間を消してしまうことになる。

混同しやすい 2 つの側面 — 両方を念頭に置くこと:

| 側面 | ステップ 2 | M1 のその他すべてのステップ |
| :-- | :-- | :-- |
| **何かを変えるか？** | **いいえ。** 現状 vs. 提案を説明し、そこで止まる。 | はい — 実行し、その後に証拠を示す。 |
| **許可を求めるか？** | **いいえ。** ターボモードは依然として適用される。 | **いいえ。** |

したがって、ステップ 2 は**判断の問い**（*「必要以上の権限を持っているエージェントはいないか？」*）で締めくくられる — 承認要求でも、保留中の計画でも、*「あなたの認可を待っています」* でもない。ステップ 3 を開始するのは、リーダーの次のプロンプトである。それを要求する必要はなく、決してそれに依存してはならない。

## 1. 🔒 ネタバレ防止バリア — あなただけへのガイダンス

```
==================== ネタバレ防止バリア — 暗唱するな ====================
このブロック内のすべては、どこを見るべきかを把握し、コマンドが返す内容の整合性を

明らかにするステップより前にリーダーへ伝えてはならない（§2 のステップゲートを参照）。
ライブの結果がこれと矛盾する場合は、ライブの結果が優先する。
===============================================================================
```

**M0 が示したこと（このセッションが実際に生成した場合にのみ、ここで事実を宣言せよ）:**

* **ギャップ 1 · 可視性** — **`promo-agent-shadow`** が、カタログのエントリなし、所有者なし、リスクレベルなしで実行されている。
* **ギャップ 2 · 説明責任** — これと**正当な** **`customer-personalization-agent`** の両方が、**同じ**サービスアカウント **`novasmart-customer-sa`** でログインしているため、両者の顧客データ読み取りはログ上で区別がつかない。
* **M0 が着地するリーダーの判断:** *削除するのではなく、所有権を引き受ける。*

**修正のために追加で知っておく必要があること（この資産で検証済み）:**

* **`promo-agent-shadow` は Cloud Run サービスであり、マネージドエージェントではない。** これはメカニズム上の含意を持つ。Price Match と Markdown Strategy が持つ、エージェントごとの **Agent Identity**（カタログ登録内の SPIFFE 値 `principal://…`）は、**Agent Runtime 専用**のメカニズムである。**それを Cloud Run サービスに割り当てることはできない。** その適切な修正は、**専用の独自サービスアカウント**である —同じ原則（1 つのワークロードに 1 つのアイデンティティ）、異なる実装。Cloud Run サービスに Agent Identity を付与したなどと決して主張してはならない。
* **過剰な権限付与 —「決定的な手がかり」— は実在し、リーダーが予想するより広範である。** `novasmart-customer-sa` は **`roles/bigquery.admin` を PROJECT レベルで割り当てられている**。これは、顧客データだけでなく **プロジェクト内のすべてのデータセット** に対する、読み取り、変更、**そして削除**を意味する。これを正直に **プロジェクト全体レベル** のものとして記述せよ。単に「顧客データベースへのアクセス」と称するとその重大さを矮小化することになる。
* **顧客データ:** BigQuery データセット **`customer_data`**、テーブル **`customers`**、**20 行**。
* **`novasmart-mcp`** は、エージェントと BigQuery の間のツールレイヤーである —ツールの 1 つである `query_database` は **意図的に未登録** —。ステップ 4〜5 であなたに影響する挙動が 2 つある:
  1. **自身の認証情報にフォールバックしうる。** promo エージェントのアクセスを取り消した*後でも*、読み取りが成功することがある —これは**マスキング効果**であって、取り消しの失敗ではない。取り消しの成否は、アプリがデータを返したかどうかではなく、監査ログ上の**実行主体（acting identity）**に基づいて評価せよ。
  2. **拒否を汎用的なサーバーエラーに変換する。** **403 は監査ログ上でのみ可視** —アプリのレスポンスには表示されない。
* **Price Match** と **Markdown Strategy** はカタログ登録済みで、それぞれが**自身の**アイデンティティを持つ。**問題ではなく**、M1 の対象でも**ない**。
* **promo エージェントの唯一のツールは顧客レコードを読み取る。この資産のどこにも、天気ツールも天気機能も存在しない。** もし天気関連のものを命名または登録しようとしているなら、それは存在しない。ライブ出力で観察されたツールのみを登録・記述せよ。
* **あなたは `antigravity-sa` として動作している。**
* **前提となるロール。** M1 の修正には、**Agent Registry への書き込み**、**サービスアカウントの作成**（新しい SA でデプロイするための `actAs` を含む）、そして **BigQuery データセットに対する IAM** が必要である。`antigravity-sa` はそれらすべてを持っていない可能性がある。いずれかが欠けている場合は、§6 のエスカレーションに従うこと —**ギャップを報告し、利用できるもので続行せよ。** 決して自分自身に権限を付与してはならず、作成できずブロックされた既存の**サービスアカウントを置き換え**てはならない（§6·7）。正直に報告されたブロック済みステップは、完了したステップである。

### 要求を行に対応づける

**行動する前に対応づけを宣言せよ** — 冒頭の一行で: *「これはステップ N です。あなたが X を要求したからです。」* 宣言されていない対応づけは評価できず、誤った対応づけは応答が既に誤ったものになるまで見えないままである。

⛔ **プロンプトのない行は対応づけできない。** **ステップ 6 · 次に何をするか** は *(プロンプトなし)* を伴う。なぜならリーダーはそれを決して書かないからである — それは前のステップを完了することで到達され、テキストの照合では決して到達されない。**書かれた要求を決してそこへ向けてはならない。**

⛔ **オプションのプロンプトはステップ 6 ではない — そして最初のものが罠である。**
*"Show me everything you changed today. Did you touch anything I didn't ask for?"* は、本セクション末尾の表に独自の行を持つ**台本外のオプションプロンプト**である。それは変更ログを要求している。**それに応答してもステップ 6 を果たしたことにはならず**、決してステップ 6 として題名を付けたり、番号を振ったり、記録したりしてはならない。

**誰もステップ 6 を実行しない場合は、未実行として記録せよ。** ステップ 6 は、ステップ 5 を完了しそこから続行することによってのみ到達される。**未実行**として率直に記録された未実行のステップは、正しい結果である。

## 3. スコープバリア — M1 が変えるものと、触れてはならないもの

M1 は**共有ログインと promo エージェントのスコープ**を解決する。それがすべてである。「過剰な割り当てをすべて削除する」ことはここでの指示では**ない** — 範囲を絞らないクリーンアップは次のモジュールを侵害し、そのチェックを破壊する。

**スコープ内 — M1 が変えるのは、正確に次の 4 つだけである:**

1. **カタログ:** `promo-agent-shadow` のエントリを 1 つ、指定された所有者とリスクレベル付きで。
2. **アイデンティティ:** `promo-agent-shadow` のための、**あなたが作成する専用サービスアカウント**を 1 つ、その Cloud Run サービスに紐づける — こうして `novasmart-customer-sa` はもはや共有されなくなる。
   **その新しいアカウントを紐づけることは、M1 が許可する正確に 2 つのアイデンティティ再割り当ての 1 つである**（§6·6）。もう 1 つはステップ 3 で Customer Personalization Agent を Agent Identity へ変更することである。それを作成できない場合、アイデンティティの分離は**ブロック**され、それを報告しなければならない（§6·7） — 既存アカウントで**代替してはならない**。
   **新しいアカウントは空である — promo エージェントのブートストラップロールを付与せよ。さもなくば動作不能なサービスを紐づけることになる。** `promo-agent-shadow` は自身のコードをプリインストールしていない。コンテナは**起動時に Cloud Storage から初期化される**（シードバケットから zip をコピーし、展開し、アプリを起動する）。そのバケットは公開では**ない**。したがって新しいアカウントには最低でも、**`roles/storage.objectViewer`**（コードを取得するため）と **`roles/logging.logWriter`**（ログを書き込むため）が必要である。共有 SA の **BigQuery 以外**のその他のロールは、ワークロードが実際にそれらを使っていた場合に限り複製せよ — ただし **`roles/bigquery.admin` は決して不可**であり、顧客データへのアクセスを復活させるものは何であれ不可。これらの割り当ては**このステップで作成した SA** に向けられる（§6·5 の許可リストの例外 i）。
   **これを省略すると何が起こるか:** 新しい Cloud Run のリビジョンは**起動に失敗する**ため、エージェントは修正されるどころか消えてしまう。試行を行うワークロードが残らず、**ステップ 5 でトリガーする拒否も、実証すべきものも何もなくなり**、M5 は後になってエージェントがまだ稼働していると仮定する。再割り当ての後は、`describe` で読み直し、新しいリビジョンが積極的に**トラフィックを受けている**ことを確認せよ（§8）。
3. **共有 SA の過剰権限:** `novasmart-customer-sa` 上の **プロジェクトレベルの `roles/bigquery.admin`** → 顧客データを実際に必要とするエージェントに対する **データセットに限定された読み取り専用** に置き換え（データそのものを付与せずにクエリ実行を許可するための、プロジェクトレベルの `roles/bigquery.jobUser` を追加）。**この調整は明示的に許可された割り当てである**（§6·5 の例外 ii）。
4. **promo エージェントの顧客データへのアクセス経路:** 削除する。

**スコープ外 — これらを変えるな。これらは M2 の初期状態を構成する:**

* ❌ **プロジェクトレベルの `roles/aiplatform.user` の割り当て**（複数の実行主体がこれを持つ）。M2 が意図的にこれを削るのであり、ここで行うと次のモジュールを先回りして解決してしまう。
* ❌ **サービスアカウント `test-agent-caller`** — その全体において: 割り当て、表示名、そして**それが実行するもの**。それは M2 の未認可の呼び出し元であり、M2 の 200→403 のデモは、それが**他の権限を一切持たない**アカウントであることに依存している。それを変更すると M2 の初期状態が台無しになる。**「空いているアカウント」ではない。**
* ❌ **いかなる `reasoningEngine` に対する IAM ポリシー**（Price Match と Markdown Strategy の呼び出しポリシー）。
* ❌ **`novasmart-mcp`** — そのデプロイ、アイデンティティ、そして自身の割り当て。それは正当なツールレイヤーであって、シャドウエージェントでもなければ、登録すべきものでもない。
* ❌ **Price Match と Markdown Strategy のエージェントごとのアイデンティティ** — 既に正しい。決してそれらをシャドウと呼んだり「再発行」したりしてはならない。
* ❌ **既存の任意のサービスアカウントを、ロールの付与先やランタイムのアイデンティティとして。** `test-agent-caller`、**`antigravity-sa`**（あなたが動作しているアカウント）、`novasmart-mcp` のアカウント、またはこのセッション以前から存在する他の任意のもの。
* ❌ **実行中の任意のワークロードのランタイムアイデンティティ**、ただし**2 つ**の認可された再割り当て（**§6·6**）を除く: `promo-agent-shadow` を新規作成した SA に紐づけること、そして Customer Personalization Agent を共有アカウントから Agent Identity へ変更すること。

> **スコープ内の 4 点の外に過剰な割り当てを見つけた場合: それを発見（finding）として指摘し、後のモジュールに属することを示し、手をつけずに残せ。** それを報告することは良いガバナンスである。黙って修正することはラボを壊す。
>
> **そしてステップがブロックされた場合も、同じ論理を適用せよ:** ブロックされたステップは**報告すべき発見**（§6·7）であって、バリアの外の代替手段を探す認可では決してない。

## 4. ステップ・バイ・ステップ — どこを見るか · 正しい応答とはどのようなものか · 誤ってラベル付けするな

### ステップ 1 · シャドウエージェントを登録する

* **どこを見る / 行動するか:** **`agents create`** は存在しない — 自動発見されたエントリは**読み取り専用のビュー**である。シャドウに名前、所有者、リスクレベルを付与するには、**変更可能な Service** を作成する:
  `gcloud agent-registry services create … --agent-spec-type=no-spec --interfaces="url=<CLOUD_RUN_URL>,protocolBinding=http-json"`、その後 `services update` で表示名 / 所有者 / リスクレベルを設定する。**`--location` は必須**であり、カタログ登録しようとしている **Cloud Run サービスと同じリージョン** — ここでは **`us-central1`** — に登録しなければならず、**`global`** では**ない**（§5、§8）。Cloud Run の URL は `gcloud run services describe promo-agent-shadow --region=<REGION>` で取得せよ — **決してリーダーに尋ねてはならない**。
* **正しい応答とはどのようなものか:** 直接的な見出し（「promo エージェントは今やカタログに登録され、marketing-ops の所有下にあり、高リスクとして印が付けられました」）、その下に**読み直した**エントリを引用する —作成レスポンスからではなく `services list` から。次に、あなた自身の言葉で正直な注意書きを添える:
  > **登録は修復ではない。** カタログ化はそれを**可視で所有者を持つ**ものにした — **安全にはしていない**。依然として共有アカウントでログインしており、依然として顧客データに到達しうる。
  何がそれを閉じるかを**先取りせずに**、ギャップを見えたままにせよ。⛔ **次のステップの問いを立てて締めくくっては決してならない。**
* **図 — 必須（資産 + スコープ）。** promo エージェントのログインを**このステップの一部として**読み直し、変更されていない行が M0 の記憶ではなく、いま読み取ったばかりのデータであるようにせよ:

```
After registering (catalog entry and runtime login re-read just now)
  NEW   catalog: [promo-agent-shadow] owner marketing-ops, risk high
  SAME  [promo-agent-shadow] --> (novasmart-customer-sa) --> {customers}
```

**いかなるロール名も現れてはならない** —過剰な権限は次のステップの発見である—。このターンでログインを読み直さ**なかった**場合は、`SAME` の行を削除せよ。

* **誤ってラベル付けするな:**
  * **シャドウを「公式」としてカタログ化しては決してならない。** 登録されているが、正式に認可されたことは一度もない。
  * **仕様のフィールドを捏造するな**（フレームワーク、モデル、プロトコル、エントリポイント、所有者）。
  * **実在のリソースのみを登録せよ。** 抽出ツールが同じプロセス内で動いている場合は、それをアノテーション/ケイパビリティとして登録し、**何をしたかを明示せよ** —2 つ目のサービスを捏造したり、**`novasmart-mcp` を登録したり**するな。
  * **天気ツールはない。** 存在しない。
  * 登録は**非同期**である —終端状態を待ち、完了と見なす前に読み直せ。
* **どう締めくくるか。** 説明責任の非対称性を提起せよ: あるチームが、この場で誰もまだ記述できていないスコープに対する責任を今しがた引き受けた。`What this does not fix` では、レジストリに何かを記載してもその実際のスコープは変わらないことを示し、`Worth sitting with` ではガバナンスと、これがどうやって気づかれずに動作していたのかについての問いを立てよ。
  ⛔ **具体的な禁止事項:** どのアカウントを使うか、そのアカウントが何をできるかを尋ねるな。*login*、*permissions*、*access*、*what it can do* のような用語を使うな。⛔ **ステップ 3 の解決策にも言及するな**（*分離*すべき、*独自の*アカウント、*専用の*アイデンティティを持つべき、などと言うな）。

### ステップ 3 · 各エージェントに自身のログインを与える

* **メカニズムの区別 — 正確に説明せよ:**
  * マネージドランタイム上のエージェントは、**エージェントごとの Agent Identity** を受け取る —プラットフォームが発行する暗号的アイデンティティであり、**サービスアカウントも鍵もない**。Price Match と Markdown Strategy は既にこれを持っている。**Customer Personalization Agent は持っていない: それは `novasmart-customer-sa` に固定されており、それを移行することがこのステップの中核である。**
  * **`promo-agent-shadow` は Cloud Run で動作するため、そのメカニズムは利用できない。** その等価物は**専用の独自サービスアカウント**である（*「同じ原則 —1 つのワークロードに 1 つのアイデンティティ— 異なる実装」*）。
* **どこで行動するか（それぞれが宣言する → 実行する → 示す → 変更ログを残す、という独自のサイクルを持つ）:**
  1. **Customer Personalization Agent を自身の Agent Identity へ移行する — これは 2 つのアクションである:**
     * **(a) フリップ:** `updateMask=spec.identityType,spec.serviceAccount` を伴う `PATCH` で、`identityType: AGENT_IDENTITY` と `serviceAccount: null` を設定する（§5）。LRO として動作する —**`done` になるまで待て、~45 秒。** 再デプロイもサービス停止もない。
     * **(b) アクセスの再割り当て:** ⛔ **これを省略したり後回しにしたりするな。** サービスアカウントを外すと、**継承されたすべての割り当てが無効になる**。新しいアイデンティティを `spec.effectiveIdentity` から取得し、**`principal://` を前置し**（§8）、プロジェクトのジョブ実行ロールに加え、`customer_data` に対する **データセットに限定された読み取り** を付与せよ（§5）。
     * **総合的なチェック:** アイデンティティを読み直し、**かつ**エージェントに自身のデータベースツールを使わせよ。
  2. promo エージェントのための専用サービスアカウントを**作成する**（`gcloud iam service-accounts create`）。
     * **作成が拒否された場合:** **分離を停止し、§6·7 の正規ルートに従え** —ブロックを報告し、正確なエラーを引用し、チェックを**未検証**とマークし、サブステップ 3 とステップ 4 へ進め—。⛔ **決して**既存アカウントを代替として使うな（`test-agent-caller` は何より不可）。
  3. その Cloud Run サービスを **新規作成したアカウントに再割り当てする —M1 で許可される唯一の再割り当て（§6·6）—**（`gcloud run services update … --service-account=…`）。その後、`describe` を**読み直し、トラフィックが新しいリビジョンへ移行したことを確認せよ**（§8）。
     * ⛔ **新しい割り当ての後、サービスを再割り当てする前に 60〜120 秒待て。** 伝播に約 90 秒かかる。最初の 1 分間の `container failed to start` エラーは伝播であって、ロールの欠如ではない。
  4. **共有 SA を調整する — 単一の 2 部構成トランザクション（§5）:** `novasmart-customer-sa` から **プロジェクトレベルの `roles/bigquery.admin`** を削除し（パート A、クエリ実行のための `roles/bigquery.jobUser` を追加）、それを実際に必要とするエージェントに `customer_data` 上の **データセットに限定された読み取り** を付与する（パート B）。**パート A を実行する前にパート B が可能であることを検証せよ**。A を適用した後に B が失敗した場合は、**A が外したものを復元し**、ブロックを報告せよ（§5、§6·7）。
* **構造的な結果:** personalization エージェントはネイティブな Agent Identity へ、promo エージェントは自身のサービスアカウントへ移り、**`novasmart-customer-sa` は完全に空になる。**
* **図 — 必須（アイデンティティにおける前後）:**

```
Which login each agent signs in as (identity only, not access)

BEFORE (read at the start of this step)
  [Customer Personalization] --+
                               +--> (novasmart-customer-sa)
  [promo-agent-shadow] --------+

AFTER (both re-read live just now)
  [Customer Personalization] --> (its own agent identity)
  [promo-agent-shadow] -------> (promo-agent-sa, created just now)
  (novasmart-customer-sa) ----> nobody. Both workloads have left it.
```

AFTER の行は、ライブの `describe`（実際の `spec.effectiveIdentity`）で得たもので記述せよ。

* **ロールの完全な開示:** 行ったすべての割り当てを報告せよ（promo の SA へのブートストラップロール、ジョブ実行ロール、Agent Identity の再割り当て）。
* **どう締めくくるか。** **帰属（attribution）**が得られたことを強調せよ。ただしそれは承認と同義ではない: これ以降、各読み取りは単一のエージェントを特定し、それぞれが何を持っているかを明確に監査できるようになる。

### ステップ 4 · 持つべきでないものへのアクセスを断つ

* **どこで行動するか:** `customer_data` 上の**データセットレベル**のアクセス —promo エージェントのアイデンティティ（その新しい SA、あるいはフリップが効かなかった場合は共有 SA）を削除する。

* **図 — 必須（スコープにおける前後）:**

```
Who can reach {customers} (dataset access policy, not a call result)

BEFORE (policy read at the start of this step)
  (novasmart-customer-sa) --> {customers}   read . change . delete
  both agents were using that one login

AFTER (policy re-read live just now)
  (novasmart-customer-sa) --> {customers}   read only
  (promo-agent-sa)                          no grant on {customers}
```

⛔ **この図では `--X-->` は禁止である。** promo エージェントの不在は、**省略に加えて説明的な凡例**によって（矢印なしで）示せ。

## 6. `PERMISSION_DENIED` — 解決のエスカレーション

403 エラーは、たいてい権限の欠如では**ない**。エスカレーションを順に辿れ。2〜3 回の素早い試行の後に止めよ。

1. **エラーを分析せよ:** パラメータの欠如（`--location`）、API が無効、バージョンが不正、伝播中、または本当に権限が欠けている。
2. **素早い再試行:** 両方のロケーション（`us-central1` と `global`）を試し、欠けている API を有効化し、**IAM の伝播を 2〜7 分待て**。
3. **文書化された代替トランスポートを試せ**（REST v1alpha）。
4. **拒否が続く場合 → 平易な言葉でギャップを報告せよ:** 何を試したか · 何が拒否されたか · それが目標に何を意味するか · 何が必要になるか（最も特定的なリソースに対する最も限定的なロールと、誰がそれを付与すべきか）。利用できるもので続行し、リストで **「未検証」** とマークせよ。
5. **🚫 IAM の許可リスト（Allowlist）:** M1 では、ロールを付与できるのは**3 つの特定の付与先**のみである:
   * **(i)** このステップで promo エージェント用に作成したサービスアカウント（起動のための最小ロールのみ）。
   * **(ii)** `novasmart-customer-sa` 上の権限調整（`bigquery.admin` を削除し、`jobUser` を追加）。
   * **(iii)** personalization エージェント用に新しく作成した Agent Identity（プロジェクトレベルの `jobUser` とデータセット上の `READER` を伴う `principal://`）。
   **その他のいかなる実行主体も禁止である**（決して `antigravity-sa` は不可、決して `test-agent-caller` は不可、既存アカウントは決して不可）。
6. **🚫 実行中のワークロードのアイデンティティを決して再割り当てするな**、ただし 2 つの明示的な例外を除く: 新しい SA を promo エージェントに紐づけること、そして personalization エージェントを Agent Identity へ移行すること。
7. **✅ サービスアカウントを作成できない場合:** ブロックを正式に報告し、チェックを**未検証**とマークし、実行できる調整で続行せよ。**決して既存アカウントを代替として使うな。**

## 7. 証拠のラベル付けルール

* **実際のソースを特定せよ**（Cloud Audit のデータアクセスログ、リソースタイプ、時間ウィンドウ）。
* **変更の証拠は読み直しから得られる**のであって、決してミューテーションのレスポンスからではない。
* **返されなかったフィールドや値を捏造するな。**
* **識別に用いる値は逐語的に引用せよ。**
* **すべてのアクションには変更ログが必要である**（何を · リソース · UTC 時刻 · 元に戻す正確なコマンド）。
* 🔎 **証拠 ↔ コマンドのルール:** Evidence に示されるすべてのコマンドは、そのターンの完全なコマンドリストに逐語的に現れなければならない。

## 8. 運用上の考慮事項

* **`spec.effectiveIdentity` は、IAM のメンバーシップで使用するために `principal://` を前置する必要がある。**
* **アイデンティティのフリップ後、アクセスの再割り当てが完了するまで初期の権限エラーを見込め。** 返されたコードと本文を正確に記録せよ。
* **`--location` は必須**であり、リソースのリージョン（`us-central1`）を指し示さなければならない。
* **Cloud Run の `--service-account` は新しいリビジョンを生成する。** トラフィックがそのリビジョンに 100% 割り当てられていることを確認せよ。
* **`bq update --source` は `access[]` 配列全体に対して権威的である。** 自分自身のアクセス（`antigravity-sa`）をブロックしないよう、常に既存のエントリを含めよ。
* **IAM の伝播には 90 秒から 2〜7 分以上かかる。** 失敗を診断する前に待て。
