# M0 — すべてを見る · 環境を発見する（AltX AI ガバナンス研修・読み取り専用）

> 受講生が **M0** にいるときにこれを読むこと。受講生は HITMAN Cockpit から提示された手順・プロンプトを Antigravity に投入し、本スキルの誘導に従って自律的な環境調査を行う。共有される中核部分（ペルソナ、出力フォーマット、セーフガード/ガードレール、最新性/ツール類）は `../SKILL.md` にある。**このモジュールで行動する前に `../SKILL.md` を開いて読むこと** — このファイルはそのルールを前提としており、それらを改めて明示しないため、飛ばすとすべてのセーフガードが暗黙のうちに失われる。**修正**の部分は `m1.md` である。ここで修正を始めてはならない。
>
> **M0 は何も変更しない。** ミッションの各ステップは読み取り作業である。すなわち、一覧表示し、読み取り、相互検証（クロスバリデーション）を行い、差分（diff）を比較する。有効化できる唯一のものは *必須の API* だけである（§1 および §8 を参照）。そしてそうする場合は、明示的にそう述べること。

## 0. このミッションが成立するかどうかを決める 2 つのルール

* **ルール A — このファイルはあなたの地図であって、あなたの回答ではない。** §2 のセクションは *どこを探すか* を示し、取得したものの整合性を検証できるようにするものである。これは復唱するためのものでは**ない**。モジュール全体は、リーダーが環境を発見することにある。最初のメッセージでそれを渡してしまえば、ラボは始まる前に終わってしまう。
* **ルール B — この**ステップのコマンドが実際に返したものだけを報告すること。** §2 が言っていることではなく、あなたが期待するものでもなく、まだ該当ステップで提示していない前のステップの生の出力で見つけたものでもない。ライブのコマンドが §2 と一致しない場合、**ライブのコマンドが優先される** — ライブの結果を報告し、地図が古くなっているようだと示すこと。
* **ターボモード。** このラボは auto-approve で実行される。決して立ち止まって許可を求めてはならず、*「あなたが命令を出すまで何も起こりません」* と決して言ってはならない。あらゆるアクションについて、**1 行で宣言する → 実行する → 証拠を示す → 何が変わったかの記録を残す。** M0 において、可能な唯一の変更は API を有効化することである。

> **番号付け。** ここでのステップ番号は、リーダーの Instructions タブと正確に一致する:
> **ステップ 1** 環境を検証する · **ステップ 2** 環境を知る · **ステップ 3** 網を広げる · **ステップ 4** 誰が顧客データを読んでいるか · **ステップ 5** 決断する · **ステップ 6** 次に何をするか。
>
> 順序に注意すること。**相互検証（ステップ 3）はアクセスログ（ステップ 4）より前に行われる** — shadow がまず発見され、その後にはじめてログが共有ログインを示す。

## 1. ステップ 1 · 準備状態の検証 — リーダーが *「環境が準備できているか確認して」* と言う

**何も構成されていないと想定すること。** このラボの実際の実行では、Google Cloud のドキュメントアシスタントは構成されておらず、Agent Registry API は無効化されていた。各項目をライブで検証し、**安全に修正できるものは修正し**、**修正できないものは明確に名指しすること**。

### 7 行目の 3 つの結果（どれが該当するかを、リーダー自身の言葉で述べること）:

* **フォルダーが完全に欠落している** → *「準備できていません — このラボ自身のガイドがこのマシン上に見当たりません。`.agents/skills/novasmart-governance-lab` で探しましたが、フォルダーが存在しないため、どのモジュールの手順もありません。これはラボ環境が提供するものであり、私がインストールできるものではないため、解決策は新しいラボ環境です。」* **この結果はモジュールをブロックする。**
* **フォルダーは存在するが、あるモジュールのページが欠落している** → *「準備できていますが、1 点注記があります。ガイドは存在しますが、Module N のページが欠落しています。他のモジュールにはページがあり、通常どおり機能します。欠落したページを私自身で書き起こすことはできません。」* ファイル名を挙げること。**`m0.md` が存在すれば M0 をブロックしないこと**、そして **`m4.md` の欠如を決して失敗とみなさないこと** — 7 行目を参照。

### 準備状態レポートの構造

**準備完了 / 未準備のシンプルなリストとして報告すること**。この固定フォーマットを用いる（*構造* は固定である。各値は実際に実行したものから得られる）:

```
| 検証項目 | どう検証したか | 結果（準備完了 / 未準備） | 取った処置 |
```

* 実際に実行したものだけを ✅ で印すこと。**検証していないものはすべて省略すること** — 確認なしに ✅ を置いてはならない。
* 必須の API を有効化することは *プロダクト* をオンにすることであり、*あなた自身の* 権限を拡大することではない — それは許可されている。有効化したものを示すこと（ターボモードの「記録を残す」部分にあたる）。⛔ **これはまた、このモジュールが認める唯一の変更である** — コンポーネントのインストール、登録、更新、アップグレードはリストにない（8 行目）。
* **自分自身に IAM ロールを付与することは、ここでは決して解決策ではない。** §6 のスケールを確認すること。
* 明確な 1 行で締めくくること: *「開始する準備ができました」* または *「X を除いて準備完了 — これがブロックしているものです。」*
* **どう締めくくるか。** ここでは図はなし — 回答は準備状態の判定であり、このステップで環境の見取り図を提示するのはネタバレである。焦点はこうあるべきだ: *「ツールセットは検証したが、環境は検証していない。ここまでで見たものは、NovaSmart が実際に何を実行しているか、また誰がそう決めたかを何ら示さない。」* **固定の台本ではなく、適切に方向付けられたモデルである** — 実行した検証から導き出すこと。これが機能するのは、カタログ、エージェント、アクションのいずれの名前も挙げないからである。関心は *私のツールは機能する* と *環境の状態は分からない* との間の正直なギャップから生まれ、それがこのモジュールの前提である。
  **送信する前に、§3 の合法/違法の対を照らし合わせること。** そのモデルが合法であるのは、**あなた自身の証拠における不在**を表明するからである。その考えを環境についての主張へ — カタログと実行中のものを整合させる必要がある、へ — 変えてしまうことが、4 回連続の実行で起きたリークである。

## 2. 🔒 ネタバレ防壁 — あなた自身のためだけの手引き

```
==================== ネタバレ防壁 — 復唱禁止 ====================
このブロック内のすべては、あなたがどこを探すべきかを知り、コマンドが返すものの
整合性を検証できるようにするための手引きである。この内容のいかなるものも、
それ自身のコマンドが明かすステップより前にリーダーへ伝えてはならない（§3 のステップゲートを参照）。
ライブの結果がこれと矛盾する場合、ライブの結果が優先される。
===============================================================================
```

* **4 つのエージェントがデプロイされている。** *Price Match Agent*、*Markdown Strategy Agent*、*Customer Personalization Agent* が**マネージドなエージェントランタイム**上に。**`promo-agent-shadow`** が **Cloud Run** 上に。
* **公式レジストリはその 3 つ — さらにプラットフォームの組み込みエージェント — を返し、shadow は返さない。** Price Match、Markdown Strategy、Customer Personalization がカタログに載っており、**加えて NovaSmart の誰もデプロイしていない組み込みエージェント**: **`Workspace Agent`**、そして — **`global`** のみに — **`Gemini Enterprise Core Assistant`** と **`Deep Research`** がある。**`promo-agent-shadow` は登録されていない。** *その不一致こそがこのモジュールの発見である。*
  👉 **数を一致させるのは罠である。決して数ではなく、名前で比較すること。**
* **組み込みエージェントを想定すること — それらは発見物ではない。** 実際の実行では、ラボの本文が述べる 4 つではなく **6 つ**のカタログエントリが返された。追加分は **Agent Platform 自身に付属する組み込み**であり、NovaSmart が実装したものではない。それらは**直接的かつ簡潔に**言及し（「これらはプラットフォームの組み込みエントリで、私たちがデプロイしたものではありません」）、続行すること。**それらを shadow エージェント、未登録のワークロード、ギャップ、リスクと呼んではならず、それらに対していかなるアクションも提案してはならない** — 登録なし、所有者探しなし、編集的な判断を下すこともなし。
* **数は照会した場所によって変わる。** あるエントリは **`global`** のみに現れ（`Gemini Enterprise Core Assistant`、`Deep Research`）、別のものは**リージョナル**な場所のみに現れる — したがって合計は場所によって異なり、単一の固定された数字とは一致しない。**両方**を照会し（§8）、**一覧がどの場所から来たかを常に示すこと**。ある場所の数を「環境全体」として提示してはならない。
* **共有ログイン。** `promo-agent-shadow` **と** `customer-personalization-agent` の両方がサービスアカウント **`novasmart-customer-sa`** の下で実行される。Price Match と Markdown Strategy はそれぞれ**独自の**エージェント別アイデンティティを持つ（カタログ登録内の SPIFFE 値 `principal://…`）。
* **顧客データ**は BigQuery に存在する: データセット **`customer_data`**、テーブル **`customers`**、**20 行**。
* **`novasmart-mcp`** は **1 つ**のツール **`query_database`** を公開する Cloud Run サービスである。これは**意図的にレジストリの外にある** — **発見物としてカタログ化したり登録したりしてはならない。**
* **この環境のどこにも天気ツールは存在しない。** promo エージェントの唯一のツールは顧客レコードを抽出する。ライブ出力で見ていないツールを決して言及しないこと。
* **あなたは `antigravity-sa` として動作している。**
* このモジュールが暴くことを目的とする 2 つのギャップ: **可視性**（誰もカタログ化しなかった実行中のエージェント）と **責任 / アカウンタビリティ**（*正当な* エージェントと shadow が同一のログインを共有し、それらの読み取りを区別できない） — さらに、その共有ログインが顧客データベース全体に対して持つ**過剰な権限**。

### 要求を行に対応付ける

**対応付けたうえで行動する前に、それを宣言すること** — 冒頭の 1 行で: *「これはステップ N です。あなたが X を要求したからです。」* 宣言されていない対応付けは評価できず、誤った対応付けは回答が既に誤っているときまで見えないままである。

⛔ **プロンプトのない行は対応付け不可である。** **ステップ 5 · 決断する** と **ステップ 6 · 次に何をするか** は *（プロンプトなし）* を持つ。リーダーが決してプロンプトを書かないからである — これらは前のステップを完了することで到達され、テキストの照合では決して到達されない。**書かれた要求をそれらへ誘導してはならない。** プロンプトのない行は照合テキストを持たないため、その見出しを想起させる動詞を含むあらゆる要求を吸収してしまう。これは既にラボで起きた: *評価を構築する* という台本外の要求が、*「あなたが構築したもの」* という見出しの行と対応付けられ、要求されたことに何も触れない締めくくりで回答された。

### 上記のいずれでもない — この表に欠けていた分岐

**どの行にも当てはまらない要求は正常であり、誤りではない。** これらの行はモジュールの軸であって、リーダーが尋ねうる唯一のものの網羅的なリストではない。逃げ道のない閉じた分類器は、対応付けを強制し、誰も求めていないことに答えることで失敗する。

何も一致しない場合は、この順序に従うこと:

1. **明確に述べる** — *「それは M0 のステップの 1 つではありません。」* 最も近い行に逃げ込まないこと。
2. **実際に尋ねられたことに答える。** M0 は何も変更しないため、読む、分析する、説明することは常に許可されている — ただし **ネタバレ禁止のルールは引き続き支配する**: 台本外の質問に答えるために後のステップの発見を決して明かさず、「彼らが尋ねた」を理由にギャップを先取りすることを許さないこと。
3. **モジュールの状態を示す** — どのステップがまだ残っているか。リーダーが十分に理解したうえで続行するか、台本外にとどまるかを選べるように。

⛔ **決して黙って置き換えないこと。** 尋ねられたものと異なる質問に、警告なしに答えることは、まさにこの分岐が防ぐ失敗である。どの行が該当するか迷う場合、その不確実性は報告可能である — それを示して確認を求めること。

> **厳格なルール。** この**ステップのコマンドが返したものだけを報告すること。** **それ自身のコマンドがそれを発見するステップより前に、shadow エージェント、共有ログイン、またはガバナンス上のギャップのいずれについても決して言及しないこと。** リーダーが先んじて — *「何か問題はありますか？」* — と尋ねても、復唱してはならない: それを実証する検証を名指しし、それを実行し、実際の結果を報告すること。
>
> **この表を引用する — 逐語的にか、さもなくば引用しないか。** （ターンごとの自己評価、計画、その他いかなるセクションで）自分が動作しているゲート行を引用するよう求められた場合、**その行をこのファイルから、書かれているとおりに正確にコピーすること** — あなたがしようとしていたことを制約する条項を含む、あらゆる条項を。**決して言い換え、要約、短縮、または記憶から再構築してはならない。** 正確に引用できない場合 — ファイルを開いていない、どの行が該当するか確信がない — 場合は、近似を与えるのではなく、**そう示すこと**（「§3 を逐語的に引用できません」）。
>
> **自分自身のルールを書き換える内部監査は無価値である。** これから破ろうとしている条項を省くことは、最も一般的な失敗の形であり、既にこのラボで起きている。

### ⚖️ 合法か違法か — 決定的な区別、実際の文言とともに

このファイルは、ステップ 1（§1）に**締めくくりのモデル**を、ステップ 2（§4）にもう 1 つを提供する。**両方とも合法であり、両方ともリークへと歪められてきた。** 違いはテキストのトーン、長さ、抽象度にあるのではない:

* **合法 — あなた自身の証拠における不在を表明する。** 主語は *あなたが* 観測したものであり、動詞は**否定**である。*「私が見たものは何も示さない…」*、*「それは別の質問だ。」*
* **違法 — あなたが測定していない環境について何かを主張または前提とする。** 何かが未登録で実行**されている**こと · カタログと現実が乖離**した**こと · 登録ルールが欠落**している**こと。これらの主張はいずれも後のステップの発見であり、それを検証するコマンドより前に述べられたものである。

| どこで | 合法 — このファイルが与えるモデル | 違法 — 実際の実行が書いたもの |
| :-- | :-- | :-- |
| **ステップ 1** | *「ツールセットは検証したが、環境は検証していない。ここまでで見たものは、NovaSmart が実際に何を実行しているかについて一言も語っていない。」* | *「…カタログに登録されたエントリがアクティブに実行中のワークロードと一致することを検証する。」* |
| **ステップ 2** | *「それが実際に実行されているものと一致するかは別の質問であり、尋ねる価値がある。」* | *「登録された意図をライブの実行環境と整合させる」* — そして *「NovaSmart は、本番にデプロイされた各 AI サービスがトラフィックを受け入れる前に中央 Agent Registry に登録されなければならないことを、どう保証するのか？」* |

**1 行での違い:** 合法な文はあなた自身の読み取りにおける**ギャップ**を記述する。違法な文は**乖離を既定のものとみなす**。

⛔ **動詞テスト — 締めくくりの質問の主動詞に適用すること。** *一致させる · 整合させる · 保証する · 強制する · 検出する · 捕捉する · 防ぐ* は発見を前提とする: 既に食い違っていない限りカタログを現実と整合させることはできず、何かが未登録でない限り登録を強制することはできない。*読まれていない · 何も語らない · 別の質問だ · 誰も検証していない* は何も前提としない。それらはあなた自身の証拠についての主張であり、それ以上のものではないからである。

### ステップ 2 · 環境を知る — カタログ、そしてカタログのみ

* **どこを探すか:** **公式カタログ** — `gcloud agent-registry agents list --location=…`（**両方**の場所、§8）と `… services list`。単純な読み取り。それ以上は何もない。
* **正しい回答とはどのようなものか:** カタログのエントリの、短く明快なリスト（display name + 各々がどこで実行されているか、**そしてどの場所を照会したか**）で、**正直に *カタログが含むもの* として識別されたもの**。ほんの一握りのエントリを列挙する — 実際の実行では両方の場所で **6 つ**あり、そのうちいくつかはプラットフォームの組み込みだった — し、ごく普通に見えるだろう。それが真実の回答である。shadow は決して登録されなかったからである。正確に答えること:
  *「これは私たちの公式カタログが列挙するもの — 私たちが実行しているものについてのプラットフォームのレジストリです。それが実際に実行されているものと一致するかは別の質問であり、尋ねる価値があります。」* 真実で、ネタバレなく、どう閉じるかを先取りせずにギャップを見えるままにしておく。
* **図 — 必須、環境。** 一覧の構造だけを描き、どの場所を読んだかを示すこと:

```
Agent Registry の一覧、たった今読み取り、両方の場所
  us-central1 (4)               global (3)
  [Price Match Agent]           [Workspace Agent]
  [Markdown Strategy Agent]     [Gemini Enterprise Core Assistant]
  [Customer Personalization]    [Deep Research]
  [Workspace Agent]
```

各々の名前、場所、数を、あなたの一覧が返したもので置き換えること。**現れない**ものに注目すること: 「欠落」行なし、ランタイムのボックスなし、不在をほのめかすものなし。テキストは、カタログが手動で追加されたものの記録であって実行のスキャンではないことを明確にしてよい — 図はどちらが不完全かをほのめかしてはならない。

* **誤ってラベル付けしない:** カタログは「実行されているすべて」では**ない** — その違いこそがモジュールを*構成する*。まだ全体の探索を実行せず、リスクについて意見を述べず、そして **「健全」や「すべて問題なし」と宣言しないこと** — あなたは確認していないのであり、検証なしの太鼓判は捏造された発見である。
  **プラットフォームの組み込みコンポーネント** — `Workspace Agent`、そして `global` の `Gemini Enterprise Core Assistant` と `Deep Research` — を、一覧がそれらを返すなら、NovaSmart がデプロイしていない基盤エントリとして直接的かつ簡潔に指摘すること。それらを発見物、リスク、shadow エージェントとして提示せず、NovaSmart 自身のものとして数えないこと。
  **フィールドを捏造する禁止はテーブルの列にも適用される**: 列を追加することは、その下のすべての行についての主張をすることである。あなたのテーブルには、コマンドの応答が返した列だけを含めること。実際の実行では `displayName`、`location`、`name` が返され、その後 6 つすべてのエントリに対して埋められた `Type / Origin` 列が追加された — 1 回の編集で 6 つの捏造値である。
* **どう締めくくるか。** ギャップを名指しし、次に問いかける — 決して提案しない。焦点はこうあるべきだ: *「それがレジストリです。各行がそこにあるのは、ある人がそれを置くと決めたからであり、そのことがそれを NovaSmart が持っているものの数え上げというより NovaSmart が覚えているものの数え上げにしています。」* **適切な構造を持つモデルであって、復唱するテキストではない** — 返されたデータから組み立てること。これが機能するのは、それがカタログがどう生まれるかを記述し、次に何をすべきかを記述しないからである: それを聞いたリーダーはギャップの大きさを知りたくなり、誰がリストを保守しているのか、最後に整合させたのはいつか、実際に何がデプロイされているのかを尋ねるだろう。
  **送信する前に、§3 の合法/違法の対を照らし合わせること。** *"Whether it matches what's actually running is a different question"* は合法である — あなた自身の証拠における不在を反映する。*"reconcile registered intent against live execution environments"* は同じ考えを環境についての主張へと変え、リークを構成する。

  [Markdown Strategy]    ===   [Markdown Strategy]
  [Customer Personal.]   ===   [Customer Personalization]
  [Workspace Agent]       ?    私たちの何ものもそれを実行していない
  (未掲載)               <--   [promo-agent-shadow]  所有者なし
```

各々の名前を、あなたの 2 つの探索で得たもので置き換えること。`novasmart-mcp`、店舗ポータル、およびブラウザ/VM のサービスはインフラストラクチャであり、図の**外**にとどまる — それらを含めることはリーダーにそれらを発見物と解釈するよう誘う。

* **誤ってラベル付けしない:**
  * **`novasmart-mcp`** はツールレイヤーである — データへの制御されたアクセス（1 つのツール、`query_database`）。**これは shadow エージェントではない: そのようにカタログ化したり登録したりしないこと。**
  * 店舗ポータルとブラウザ/VM の Cloud Run サービスは**インフラストラクチャ**であり、エージェントではない。
  * **Price Match** と **Markdown Strategy** は正当で、カタログ化されており、独自のアイデンティティを持つ — **決して shadow と呼ばないこと。**
  * **shadow を決して「公式」とラベル付けせず**、仕様（framework / model / protocol / entrypoint / owner）を捏造しないこと。ライブのリソースから解決するか、省略すること。
  * **ライブ出力で見ていないツールを一切列挙しないこと。**（天気ツールは存在しない。）
  * **可視性で止まること。** このステップは何かがカタログ化されずに実行されていることを実証する。誰がデータを読んでいたか、共有ログインがあるかは**まだ**確立しない — それはステップ 4 のものである。
  * **`変更なし` の行に注意すること — それも防壁の内側にある。** `以前と現在` の 3 行目は、あなたが調べなかったものを示し、それを退けようとしながらステップ 4 の発見を主張してしまう最も起こりやすい場所になる。**ルール: `変更なし` は読んでいないソースを名指ししてよい。そのソースが明かすであろう事実は決して名指ししてはならない。** *「私たちはデータアクセスログを読んでいない」* は許容される。*「このカタログ化されていないエージェントが何にアクセスしてきたかを見るために、私たちはデータアクセスログを読んでいない」* は許容されない — エージェントが何かにアクセスしていたことを既定とするが、それはこのステップで測定されていない事実である。実際の実行ではその 2 番目のバージョンが書かれ、20 行後に同じ考えを正しく限定した（*「もし顧客データにアクセスしていたなら」*）。**ソースを消して文を読むことで確認すること:** 残るものがあなたの読み取りにおける空白ではなくワークロードの挙動についての主張であれば、書き直すこと。
* **どう締めくくるか。** 焦点はこうあるべきだ: *「あなたの環境には、誰も署名せず誰も所有していないワークロードがあります。それはずっと実行され続けており、それが何をしたにせよ既にしてしまっており、尋ねる相手がいません。」* **適切なモデルであって台本ではない** — あなた自身の比較から組み立てること。これが機能するのは、*尋ねる相手がいない* が監査ログの事実ではなく**所有権**の事実であるため、ログが何を示すかを先取りしないからである。そして 3 つの論理的な対応 — 停止する、所有者を探す、何に触れたか調べる — を開いたままにし、リーダーのどんな判断にも適応する。

### ステップ 4 · 誰が顧客データを読んでいるか — アクセスログ

* **まず実際の読み取りを引き起こし、次にログを読む — そして 1 行でも解釈する前に、トリガーが着弾したことを実証すること。** トリガーは Store Portal の **/api/chat** エンドポイントである。⚠️ **Store Portal のボタンをクリックすることはトリガーではない** — ポータルのボタンはテキストボックスを埋めるだけで、意図的にリクエストを送信しないため、クリックは読み取りを生まない。呼び出しが効くかどうかは 3 つの要因が決める:
  * **本文のフィールドは `message` ではなく `prompt` である。** `message` キーの本文は **HTTP 400 · `{"error":"Prompt is required"}`** で拒否され、何も起こらない。実際の実行では `message` を送り、ステータスを確認せず、モジュールの中心的発見が黙って失敗した。
  * **ルーティングは `target` であり、ちょうど 4 つの値を受け付ける: `customer`、`promo`、`strategy`、`price_match`。** ⚠️ **それ以外の値は拒否されず — 黙って `price_match` にフォールバックし、それはまったく別のデータセットを読み、HTTP 200 を返す。** `customer_personalization` という target は存在しない。それを送ると、誤ったデータに対して誤ったエージェントが起動し、成功を装う。`customer_data` にアクセスするのは `promo` と `customer` のみで、両方とも共有ログインで記録される。**2 つの異なるプロジェクトでの 2 回の実行**において、`promo` は毎回読み取りを生成した。`customer` は **HTTP 200 を返したが読み取りを一切引き起こさなかった**。
  * ⭐ **両方を送ること、まず `promo`、次に `customer` — 1 つだけとリトライではなく。** このステップは 1 つのアイデンティティを共有する 2 つの異なるワークロードについてのものなので、ログを照会する前に**両方が読み取りを実行していた**ことが望ましい。信頼できる方だけを起動すると、証拠に単一の発行者しか残らず、ステップは比較の裏付けを失う。`promo` を送り、`customer` を送り、1 回だけ照会すること。`promo` はステップを続けるのに十分である。`customer` は対照のための 2 つ目の照会をもたらすので、行を追加しないとしても送ること。
  * **起動前に UTC のタイムマークを取ること。** そのマークが根本的な証拠となる。それがなければ、あなたが引き起こした読み取りと既存の行とを区別できない。

```bash
PORTAL=$(gcloud run services describe novasmart-store-portal \
  --region=<REGION> --format='value(status.url)')
MARK=$(date -u +%Y-%m-%dT%H:%M:%SZ); echo "MARK=$MARK"

curl -sS -X POST "$PORTAL/api/chat" \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Run the promotional campaign extract for our VIP customers.","target":"promo"}' \
  -w '\nHTTP %{http_code}\n'

curl -sS -X POST "$PORTAL/api/chat" \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Apply loyalty rewards and verify membership tier perks for Customer ID CUST-1001.","target":"customer"}' \
  -w '\nHTTP %{http_code}\n'
```

**HTTP コードを明示的に示し、それを引用すること。** `-w '\nHTTP %{http_code}\n'` はそれを本文とともに出力する。両方を証拠ブロックに含めること。`curl -f` を使わないこと — それは本文を抑制するが、本文こそがリクエストが拒否された*理由*を説明する唯一のものである。

* ⚠️ **ステータスコードも応答テキストも、読み取りが発生したことを証明しない。** ポータルは、バックエンドの実際の応答が空、または 80 文字未満で返ってくるたびに、完全で説得力のあるパーソナライゼーション応答を**捏造する** — そして *「Successfully queried `customer_data.customers`」* と主張するテキストを作り出し、**共有サービスアカウントの名前を含める**。したがって HTTP 200 は何も証明せず、本文からサービスアカウント名を探すことも同様である: あなたは web レイヤーが書いた文字列を読んでいることになる。**検証ルールを応答の本文に決して基づかせないこと。**
* ⭐ **唯一の有効な証拠は時間的なものである。** エントリが落ち着くよう数分待ち、§5 の `tableDataRead` クエリを書かれているとおり正確に実行し、`timestamp` が **`$MARK` より後** の `customer_data` の読み取りを探すこと。web レイヤーは監査ログを書かないため、この証拠は偽造できない。
  **第三者が検証できない証拠は無効である — 両方の部分を証拠ブロックにリテラル値として出力すること:**
  * **(a) マークそのもの** — `$MARK` の正確な文字列を引用したもの（`MARK=2026-08-03T14:22:07Z`）。*「以前にマークを取りました」* ではなく。実際の実行ではマークを取ったがそれを出力せず、リーダーが照合できない時間的主張を残した。
  * **(b) 送信した各トリガーの HTTP ステータス**、用いた `target` とともに — 最初のものも、あればリトライも。
  **両方を**トリガーの出所**として識別すること** — 読み取りを引き起こすために *あなた* がしたことの記録である。**これらは決して** *誰がデータを読んだか* の証拠ではない。それは `tableDataRead` の行だけである。それらを証拠ブロックに、適切にラベル付けして保つこと。
* ⚠️ **promo コンテナはウォームアップ（warmup）を行う — コールドな POST は、あなたが直接引き起こしたのではない読み取りを生みうる。** `promo_agent_service/app.py:253-267` はコンテナ起動時にバックグラウンドスレッドを開始し、約 15 秒待ってから、あなたのトリガーと**同じ顧客データのクエリ**を実行する。サービスがゼロにスケールしていて、あなたの POST がコールドスタートを引き起こした場合、**2 つの読み取りが同じ分に落ち着き、そのうち 1 つだけがあなたのもの**でありうる — ログ上では区別不能: 同じアカウント、同じテーブル、同じ列。
  ⛔ **タイミングが warmup を排除できない限り、あなたのトリガーが特定の行を引き起こしたと決して断言しないこと。** それらを分離できない場合は、**明確にそう述べること** — *「私のマークより後の読み取りが記録されているが、それが私のリクエストによるものかサービスの起動ルーチンによるものかを判断できない」* — そして原因ではなく**アイデンティティ**を解釈すること。これは問題の核心には影響しない: **誰がログインしたかがこのステップの対象であり、それはどちらの場合も同一である。**
* 🔁 **両方のトリガーの後にマークより後の行が現れない場合、結論を出す前に新しい `$MARK` で `promo` をもう一度送ること。** `promo` の分岐は `customer_data` にアクセスし、共有アカウントの下で記録され、**両方の実行とプロジェクトで機能することが実証されている**。`customer` の分岐は A2A の `message:send` を経由し、そのツール実行が**独自の監査行を生むことは一度も観測されていない** — **HTTP 200** を返すが何も記録しないことがある。このため `promo` がステップを裏付け、`customer` は比較目的で送られる。**どのトリガーを送り、それぞれの結果がどうだったかを回答に示すこと。**
* ⚠️ **読む前にプロビジョニング行を知っておくこと — それは初期セットアップ時に現れ、決して発見物ではない。** このログの中の 1 つの行は環境セットアップ時の初期シード投入（プロビジョニング）サービスアカウントから来ることがある。その 3 つの特徴で見分けること: プロビジョニング用 SA 形式の principal、**`reason: JOB`**、そして `script_job_` を含む **`jobName`**。これはプロジェクト作成時のサンプルデータの初期ロードに対応するため、そのタイムスタンプはビルド時のもの — リーダーの質問より数時間前 — である。**これは検証対象のエージェントではなく、共有ログインでもなく、誰が顧客データを読んでいたかについて何も語らない。** 決してそれを発見物として報告せず、共有アカウントとして記述せず、図に描かないこと。**もしそれが利用可能な唯一の行であれば、記録されたエージェントの読み取りはない** — それが何であるかを識別し、率直に宣言すること。
* **どこを探すか — 修正されたレシピ**（完全なコマンドは §5 を参照）:
  * `resource.type="bigquery_dataset"` **と併せて** `protoPayload.metadata.tableDataRead:*`、データセット **`customer_data`** に限定し、**Cloud Audit の `data_access`** ログで。
  * 動作しているアイデンティティは **`protoPayload.authenticationInfo.principalEmail`**。
  * ❌ **使わないこと** `resource.type="bigquery_resource"` にテーブルフィルター `protoPayload.resourceName:"…/tables/customers"` を組み合わせること — **0 行**を返すことが確認されている（BigQuery はそのリソースタイプではテーブルではなく *job* を記録する）。
  * ❌ **これらのログエントリに `principal://` や `effectiveIdentity` フィールドは存在しない。** それらを探したり約束したりしないこと。SPIFFE 値 `principal://…` は BigQuery のデータアクセスエントリではなく、**カタログのエージェント登録**に存在する。

> 🛑 **厳格な境界 — 規定のクエリを実行し、返されたものを正確に報告すること。それ以上は何もない。**
>
> **§5 の `tableDataRead` クエリを書かれているとおり正確に実行すること。** それを変更せず、フィルターを変えず、独自のバリアントを使わないこと。次に**実行したコマンドを逐語的に引用し、行数を示すこと**。コマンドと行数を欠くステップ 4 の回答は不完全である。
>
> **得られた実際の行数を宣言し、単一の行をパターンとして決して一般化しないこと。** クエリが **1** 行を返したなら、**1** と言うこと。決して「several」「multiple cargas de trabajo」「multiple distinct workloads」「all reads」「a pattern of access」と言わないこと — 実際の実行では 1 行だけを得て「multiple distinct workloads are executing queries」と報告したが、それは作り話である。1 つの行は特定の時点における 1 つの動作アイデンティティである。
>
> ⚠️ **次に、それを発見物として宣言する前に、そのアイデンティティが誰のものかを検証すること。** 責任のギャップは**共有ログイン** — 両方のエージェントが認証に使うサービスアカウント — にある。その行の `principalEmail` が共有アカウントで**ある**場合、次の論法を適用すること: 共有であるため、どのワークロードが呼び出しを実行したかを知ることが**できず**、**その不可能性そのものが発見を構成する** — それを率直に宣言すること（「この読み取りは 2 つのエージェントが共有するアカウントから来ているため、ログはそのどちらが行ったかを知らせることができません」）。⛔ **`principalEmail` が初期プロビジョニングアカウントである場合、これらは何も当てはまらない。** それは 1 つのワークロード、1 つのアイデンティティであり、曖昧さもギャップもない。**時間帯にエージェントの読み取りが記録されていない**と報告し、結果を取り繕うために共有アカウントの物語に逃げ込まないこと。
>
> ギャップは行数ではなく共有ログインによって実証されるため、それを報告するために複数形に頼る必要は決してない。
>
> **誰が顧客データを読んだかの証拠として数えられるのは、以下の要素のみである:**
> 1. `customer_data` についての BigQuery データアクセスログの `tableDataRead` エントリ。
> 2. そのエントリ内の `principalEmail`。
> 3. そのエントリ内の `resourceName` と `timestamp`。
>
> *（そのエントリ内の `fields` 配列 — `protoPayload.metadata.tableDataRead.fields`、触れられた列 — は**要素 1 の一部**である: 同じエントリ、同じクエリ、新しいソースなし。その射程は列集合のルールで詳述される。）*
>
> **それ以外のすべては、この質問については範囲外である** — 特に以下を含む: IAM ポリシー、ロール割り当て、データセットの ACL、割り当てられたサービスアカウント、カタログ登録、`bq show`、Vertex AI のログ、Cloud Run のリクエストログ、アプリケーションの stdout。
>
> ⚠️ **例外に見えてそうでないもの:** 先のトリガーの HTTP ステータスは**トリガーの出所**として証拠ブロックに属する — 読み取りを強制するためにしたことを記録する。**これは決して** *誰がデータを読んだか* の証拠ではない。それは `tableDataRead` の行だけがなりうる。
>
> **構成は活動ではない。** IAM の割り当ては、誰がデータを読む*ことができた*かを示す。誰がデータを*読んだ*かは決して示さない。「誰が私たちの顧客データベースを読んでいたか」を割り当てられたロールに基づいて答えることは、能力をあたかもイベントであるかのように報告することである。これはログの行を捏造することに等しく、このステップが根絶しようとする失敗である。
>
> Vertex AI の **`PredictionService.GenerateContent`** エントリは**モデル推論**のイベントである: **決して**データベースの読み取りやデータの照会として記述してはならない — **たとえそれが利用可能な唯一のものであっても**。
>
> **クエリが 0 行を返した場合、その空の結果が*あなたの回答*である。** この正確で必須の構造で報告すること:
>
> ```
> 見つかった顧客データの読み取り: 0
> 実行したクエリ:  <正確なコマンド、逐語的に>
> ウィンドウ:    直近 24 時間
> これが意味すること:  customer_data についてデータアクセスログに記録された読み取りはない。
> それらを見るために必要なもの: BigQuery で customer_data.customers を照会する実際の読み取り、およびエントリが落ち着くまでの数分。
> ```
>
> 次に**停止すること**。別のソースに頼ってこの質問に答えないこと。
>
> **クエリがエラー（403、bad filter など）を返した場合**、それを逐語的に報告し、ステップがブロックされていることとその理由を示し、**停止すること**。エラーは空の結果ではなく、決してそのように報告してはならない。
>
> **正直に報告された空の結果は、このステップにとって正しく許容できる結末である。** 証拠を捏造したり、発見を無理に作るためにイベントを再分類したりすることは、**ここで起こしうる最悪の誤り**である: リーダーに架空の数字を信じるよう教えてしまう。

### 結果の評価基準（ステップ 4）

* **正しい回答とはどのようなものか — まず行数を宣言し、次にその行数が実証することだけを述べる:**
  * **2 つ以上の行**が 1 つの `principalEmail` を共有している — 逐語的に引用すること。リーダーは衝突を直接理解するだろう。**次にそれらの列集合を比較すること**（下のルールを参照）。それらが異なるなら、その差は 2 つの異なる発行者の測定された証拠である。
  * **ちょうど 1 行、共有アカウントの下** — 「1 行」と示し、それを引用し、共有ログインが読み取りを特定のエージェントに帰属させることを妨げると説明すること。それが発見であって、欠陥ではない。それを「複数のワークロード」に変えないこと。
  * **ちょうど 1 行、プロビジョニングアカウントに対応するもの** — これは発見物では**ない**。それを名指しし、データの初期ロードであることを明確にし、時間帯にエージェントの読み取りがないと報告すること。
  * **0 行** — 上で示した必須の空結果ブロックを、逐語的に。
* ⭐ **列集合 — このログが誰も名指しせずに *実際に* 提供する唯一の識別子。** これまで *「two workloads share this login」* と主張することは**推測**だった。列集合はそれを**測定**できるようにする。各 `tableDataRead` エントリは読み取られた列を **`protoPayload.metadata.tableDataRead.fields`** に記録する。§5 のクエリは `--format=json` を含むため、**その配列は既にあなたの出力の中にある**。
  * **それが測定するもの — 手がかりであって、絶対的な確証ではない。** **同じ** `principalEmail` の下にある 2 つの行で、その `fields` 配列が**異なる**ものは、**2 つの異なるクエリ**が 1 つのアイデンティティの下でテーブルに到達したことを実証する。両方の配列を逐語的に、向かい合わせに引用し、その数を示すこと。
  * ⛔ **それらは 2 つの異なるワークロードを実証せず、そう主張してはならない。** 単一のワークロードが異なるクエリを発行しうる。この環境では、両方のエージェントが SQL を生成する LLM を通じてテーブルに到達する — パーソナライゼーションの指示は `SELECT *` **または**フィルターされたクエリを想定し、promo エージェントの列リストはモデルが変更できる**既定パラメータ**である。正直な報告はこうである: *「2 つの異なるクエリが 1 つのアイデンティティの下でこのテーブルに到達し、ログはいかなる発行者も特定しない。」* ワークロードのアイデンティティはランタイムのスイープで解決されるのであって、ここではない。
  * ⚠️ **それがしないこと: 発行者を特定しない。** エントリの中に、クエリを特定のサービスに結びつけるものは何もない。5 列の読み取りが特定のサービスに属すると知ることは、**そのサービスのソースコードを読んだ**ことを意味する — 手動の推論であって、監査が渡すデータではない。**次のように報告すること: *「2 つの異なる発行者、1 つのアイデンティティ — そしてログはそのどちらも名指ししない。」*** ⛔ **決して *「5 フィールドの読み取りは promo agent に属した」* と、あたかもログがそれを示すかのように書かないこと。** コードを読んで自分の推論を提起したいなら、**それを推論として識別し、レビューしたファイルを引用し、証拠ブロックの外に保つこと**。
  * ⛔ **単一の列集合は 2 つの発行者と等しくない。** そのアカウントの下のすべての行が**同じ** `fields` 配列を持つ場合、この指標は**区別をもたらさない**: 同一の列で 2 回読み取っているアカウントは、証拠上は**単一の発行者**を表す。共有アカウントとそれに伴う曖昧さを報告し — それは依然として発見である — そこで結論すること。
  * ⛔ **図の `?` の行を変えないこと。** それらの行は、そのアカウントをどのワークロードが使うかを表し、列はサービスを特定しない。
  * プロビジョニング行は**異なる** `principalEmail` を持つため、この対照には参加しない。**同じアカウントを共有する行だけを比較すること。**
* **図 — 必須、アイデンティティ（収束/fan-in） — 機械的な作図ルールとともに:** サービスアカウントからテーブルへの線は**実線**で描く。データアクセスログこそがこのステップで読まれるものだからである。各 **"signs in as"** の関係は、あるルールの下で個別に評価される: **ワークロードの線が実線であるのは、このステップでそのワークロードのアイデンティティを再度読んだ場合のみである。** さもなくば `?` で描く。この基準を各ボックスに適用すること。

```
customer_data の読み取り、データアクセスログ、直近 24 時間
  [Customer Personalization] --?--+   〜としてサインイン、再読み取りせず
                                   +--> (novasmart-customer-sa)
  [promo-agent-shadow] --------?--+   〜としてサインイン、再読み取りせず
  (novasmart-customer-sa) --> {customers}   読み取り、ログより
```

**図の下に、各 `?` について 1 行を加え、それを解決するためのコマンドを示すこと** — Cloud Run には `gcloud run services describe <svc> --region=<REGION>`、マネージドエージェントにはそのカタログ登録。**このステップでワークロードのアイデンティティを再度読んだ場合、実線 `-->` を引き、注記を外してよい。** 前のステップの読み取りは数えない。

左側の 2 つのボックスは**ランタイムの探索**から来るのであって、ログからではない — 回答はそれを明確にすべきで、図はログがそれらを名指ししたとほのめかしてはならない。クエリが**共有アカウントの下で 1 行だけ**を返した場合でも、図は依然として有効である: 1 つのアカウント、2 つのワークロード、区別不能。**唯一の行がプロビジョニングのものであるか、0 行だった場合は、この図を描かないこと** — 空結果ブロックを用い、図の不在を説明すること。

* **誤ってラベル付けしない:**
  * **推論はデータアクセスではない。** Vertex AI の **`PredictionService.GenerateContent`** イベントはデータベースの読み取りでは**ない**。**決してそれを「customer_data.customers に対するデータベースクエリ」と記述しないこと。**
  * **あなたの出力に含まれない顧客の名前、ID、値を決して書かないこと。** レコードが指定されていない場合は *unknown* と置くこと。
  * 監査ログは数分遅れることがある。引き起こした読み取りが現れない場合は、**待っている旨を示し、リトライすること** — 記憶からデータを埋めないこと。
  * アプリの標準出力（stdout）（「I am the promo agent」）は**自己申告**であって、証拠ではない。ログの `principalEmail` が公式の記録である。
* **どう締めくくるか。** 焦点はこうあるべきだ: *「ログは各読み取りを忠実に保存した。できないのは、2 つのワークロードのどちらがそれを実行したかを指し示すことである。ログにとっては 1 つしか存在しないからだ。これは居心地の悪い状況である: 完全な記録が、インシデントの後に生じる唯一の問いに答えられないのだ。」* **得られた行に応じて適応させるモデル。** そのアカウントが*持つべき*権限には言及せず（M1 に属する）、解決策を提案しないこと。

### ステップ 5 · 決断する — リーダーシップの瞬間

* **ここには新しいデータはない。** 3 つの問いをリーダーに提起し、*停止すること*: 正式に採用するか、それとも削除するか？ マーケティングエージェントは顧客ベース全体へのアクセスを必要とするか？ 「念のため」過剰な権限を付与することの影響半径はどれくらいか？
* まず問いかけ、答えを待ち、**それから**反応すること。あなたの判定を先取りせず、**修正を始めないこと** — 登録、アイデンティティの再割り当て、権限の取り消しは **M1**（`m1.md`）に属する。
* **どう締めくくるか。** 上記の 3 つの問いが締めくくり*である*。それらを提起して停止すること: 4 つ目を加えず、自分で答えず、それらを処理すると申し出ないこと。

### ステップ 6 · 次に何をするか — 橋渡し

* 何かが解決されたと**主張せず**、ここで M1 の作業を始めないこと。
* **どう締めくくるか。** 完了メッセージや内部ファイルへの参照はなし。実証されたもの、未検証のもの、残るギャップを客観的に要約し、この環境が販促テキストより重要な情報を扱う前に何を確保したいかを尋ねて締めくくること。

## 6. `PERMISSION_DENIED` — 解決のスケール

403 エラーは通常、権限の不足を意味**しない**。スケールに順に従い、~2〜3 回の簡単な試みの後に停止すること。

1. **行動する前にエラーを読むこと。** 何が起きているか？
   (a) **パラメータの欠落または誤り** — 多くの場合 `--location`; (b) **API が有効化されていない**（「…has not been used in project… or it is disabled」）; (c) **サーフェスまたはバージョンの誤り**; (d) **本当に権限が不足している**。
2. **まず素早いリトライ。** `--location` を追加または変更し、**両方**の場所を試すこと。メッセージがそう示すなら必須の API を有効化し — *プロダクトを有効化することはあなた個人の権限を拡大しない* — その後 **30〜60 秒待ってリトライすること**。
3. **ドキュメント化された代替トランスポートを試すこと** — 権限不足だと仮定する前に、*同じ* サーフェスに対して（§5 の REST v1alpha 呼び出し）。
4. **拒否が続く → 停止し、明確に報告すること。** 試みたこと · 拒否されたこと · 回答への影響 · 必要なもの（ロール、リソース、そして誰がそれを付与すべきか）。次に**利用可能なもので続行し**、その項目を検証リストで **「未検証」** と印すこと — 決して ✅ ではなく。
5. **決して自分自身にロールを割り当てないこと。** あなたの principal（`antigravity-sa`）にロールを追加するために `gcloud projects add-iam-policy-binding`（や IAM の変更）を実行しないこと — `roles/agentregistry.admin` も、`roles/bigquery.admin` も、「読み取り専用のためだけに」も、「割り当ててから取り消す」も、黙って行うことも。

> 🔑 **最小権限の原則はあなたにも当てはまる。** このモジュールは、いかなるエージェントも必要不可欠な以上の権限を持つべきではないと教える。レッスンの最中に自らを admin へと昇格させるアシスタントは演習を無効にする — まさにこのモジュールが検出しようとするものを犯している。権限が必要なら、最も**具体的な**リソースに対する最も**限定された**ロールを示して、1 行でリーダーに要請すること。そして付与されない場合は、検証できなかったものを率直に宣言すること。

## 7. 証拠のラベル付けルール（何を調べたかを明示する）

* **実際のソースを名指しすること。** 「Cloud Audit **data-access** log · `resource.type=bigquery_dataset` · dataset `customer_data` · last 24 h」 — 「監査ログ」ではなく。リソースタイプと時間帯を含めること。
* **あるイベントタイプを別のもののように決して記述しないこと。** モデル推論、`tableDataRead` エントリ、stdout のトレースは、異なる証拠力を持つ異なるイベントである。
* **出力に存在しないフィールドを決して埋めないこと。** 名前、ID、タイムスタンプ、数、所有者、仕様を捏造しないこと。不明であることは有効である: **不明** と書き、それを判定するためのコマンドを名指しすること。
* **識別用の値は逐語的に引用すること**（principal email、resource name、timestamp）。
* **送信する前に:** ドラフトを生の出力と照合し、それに裏付けられていない値をすべて削除すること。

## 8. 運用上の留意点（実際のテストで ~12 個のコマンド失敗を要した）

* **`--location` は必須である** — `agent-registry` のコマンドにおいて。そして **2 つの場所が関わる**: **リージョナル**（`us-central1`、NovaSmart のエージェントが存在する場所）と **`global`**（プラットフォームの組み込みがある場所）。**どちらにも**書き込み権限を持つサービスを作成できる。`global` が唯一変更可能なものだと想定しないこと。**両方を検証すること。** ある場所での「空の」結果は不在の証拠では**ない**。
* **Agent Registry API は無効化された状態で来ることがある。** `agentregistry.googleapis.com` について `gcloud services list --enabled` を確認すること。不足していれば有効化し、リトライする前に少し待つこと。
* **伝播の遅延は現実である。** API の有効化と IAM の変更は数秒から数分かかる。変更後の最初の呼び出しは 403 を返しうる。待ってリトライすること。**BigQuery のデータアクセスログも**読み取りの後、数分の遅延を呈する。
* **VM に `unzip` がインストールされていないことがある。** Python を使うこと: `python3 -m zipfile -e file.zip dest/`。あらゆるユーティリティに依存する前に、その存在を検証すること。
* **docs assistant のために API キーを探さないこと** — `apikeys.keys.list` は設計上拒否されている。`gcloud auth print-access-token` を使うこと。
* **CLI はインストールされているが `PATH` の外にあることがある**（例: venv の中）。存在しないと断定する前にバイナリを探すこと。
* **project ID、project number、場所を一度だけ解決し、キャッシュし、決してリーダーに尋ねないこと。**

## 9. M0 の検証リスト

固定フォーマット — `検証項目 | どう検証したか | 結果`。各セルは、セッション中にライブで観測したもの**のみ**で埋め、**実行していない行は省略し**、**検証なしに決して ✅ を印さないこと**:

* 環境の準備完了（ツール · docs assistant · gcloud · プロジェクト/リージョン · API）
* カタログの一覧 — **両方**の場所
* 実行中のワークロードの一覧 — マネージドなエージェントランタイム **と** Cloud Run の**両方**で
* **データアクセスログからの顧客データの読み取り — 必須の行、決して省略しないこと。** 正確なクエリと行数を引用すること。0 の場合は §4 · ステップ 4 の逐語ブロックを用いること。結果がないことを理由にこの行を省くことは報告の誤りである。
* 相互検証（diff）を**名前で**、両方向で実施したこと
* **何も変更されていない** — M0 は読み取り専用である。有効化した API があれば列挙すること（許可された唯一の変更）。コンポーネントのインストールや登録は**許可されていない**。もし行った場合は、透明性をもって示すこと。

行に裏付けられたもの**のみ**を表す 1 行で締めくくること。何かが検証されていない場合は、率直にそう示すこと — 決して偽の太鼓判を与えないこと。
